# Decide which user update, delete, and restore responses this server matches

Type: grilling
Status: resolved

## Question

[Decide which later-user responses this server matches](36-decide-which-later-user-responses-this-server-matches.md) matches create, detail, password, and onboarding. The list context menu and `/admin/users/{id}/edit` also call `PUT /api/admin/users/{id}`, `DELETE /api/admin/users/{id}`, and `POST /api/admin/users/{id}/restore`. Password reset and PIN reset are that same PUT. The call shapes are in [Remaining to close](../../../docs/research/remaining-to-close.md). Where the web UI can see a behavior, match v3.3.6. A difference is allowed when the Pi cannot do it. Which of those three calls does this server answer the way v3.3.6 does?

## Comments

Recommendation accepted: all three calls match v3.3.6. Password reset and PIN reset are the same PUT. The hard-delete job removes that User's Originals from object storage, and removes the local thumbnail, preview, encoded-video, and profile files.

## Answer

`PUT /api/admin/users/{id}`, `DELETE /api/admin/users/{id}`, and `POST /api/admin/users/{id}/restore` each match v3.3.6. Each returns 200 and the admin user document from [Decide which later-user responses this server matches](36-decide-which-later-user-responses-this-server-matches.md). A missing session is 401 `Authentication required`. A session that is not an admin is 403 `Forbidden`. An id that is not a UUID is 400.

`PUT /api/admin/users/{id}` accepts any subset of `email`, `password`, `pinCode`, `name`, `avatarColor`, `storageLabel`, `shouldChangePassword`, `quotaSizeInBytes`, and `isAdmin`. Omitted fields stay as they are. The edit form sends `email`, `name`, `storageLabel`, `quotaSizeInBytes`, and `isAdmin`. Password reset sends `{ password, shouldChangePassword: true }` with a 16-character password the browser generated, then shows that password in the success modal. PIN reset sends `{ pinCode: null }`. The page treats any 200 as success and reads the emitted document for the list and the detail page. Those screens read `id`, `name`, `email`, `quotaSizeInBytes`, `deletedAt`, `status`, `isAdmin`, `createdAt`, `updatedAt`, and the avatar fields.

A password is stored as a bcrypt hash with 10 rounds. A PIN is the same hash when it is six digits. `{ pinCode: null }` stores null. The response includes neither secret. The next sync of that User sends the new `pinCode`, quota, `isAdmin`, name, and email on `AuthUserV1`. Name and email also go out on `UsersV1`. An email is stored in lower case. An email already used by a User with `deletedAt` null is 400 `Email is not available`. The same User keeping their own email succeeds. `storageLabel` `''` is stored as null. Any other label is the sanitized filename. A label already used by a User with `deletedAt` null is 400 `Storage label already in use by another account`. This PUT stores the label and leaves every Original where it is. A positive `quotaSizeInBytes` that differs from the stored cap recounts `quotaUsageInBytes` from that User's Originals before the write. `0` and null do not recount. Null still means no cap. An admin changing their own `isAdmin` is 400 `Admin status can only be changed by another admin`. Another admin can change it. A missing User, or a User with `deletedAt` set, is 400 `User not found`.

`DELETE /api/admin/users/{id}` takes `{ force?: boolean }`. The confirm modal sends `{ force: false }` or `{ force: true }`. Deleting the signed-in User is 403 `Cannot delete your own account`, and the menu hides that action. A missing User is 400 `User not found`. The config-created admin has no extra protection. Both deletes set `deletedAt` to the current time, soft-delete albums that User owns, and return the user. `force` false or omitted sets `status` to `deleted` and queues nothing. `force` true sets `status` to `removing` and queues the user-delete job immediately.

While `deletedAt` is set, that User's existing Sessions stay stored and stop validating. The next request with that cookie is 401 `Invalid user token`. Login does not find the email. `GET /api/admin/users/{id}/sessions` returns `[]`, so the detail page draws no devices. Statistics and preferences still return 200. The upload heatmap is 400 `User not found`, and the detail page has no error branch on that call. Album shared links for the soft-deleted albums stop resolving. An individual shared link still opens. Likes and comments that User wrote drop off the activity list and stay stored. `UsersV1` includes `deletedAt`. The phone's user upsert ignores that field, so the invite list keeps the User until the hard delete.

`POST /api/admin/users/{id}/restore` clears `deletedAt`, sets `status` to `active`, and clears `deletedAt` on albums that User owns. The same Sessions validate again. Album shared links and the activity list come back. A missing User is 400 `User not found`. The detail page offers restore only when `deletedAt` is set and `status` is `deleted`. A User with `status` `removing` can still be restored if the row is still there.

The user-delete job removes that User's Originals from object storage, then the local thumbnail, preview, encoded-video, and profile files for that User. It then deletes albums that User owns and deletes the User row. Assets, Sessions, shared links, memories, and activity rows that belong to that User go with the row. Sync sends `UserDeleteV1` with `userId`, and album members receive the album deletes v3.3.6 already sends. Cascaded Asset deletes do not emit an asset-delete sync line. When the row is gone, the server broadcasts `on_user_delete` with the user id. The list drops that row. An open detail page returns to the user list.

The nightly cleanup queues that same job, without force, for each User whose `deletedAt` is older than `user.deleteDelay` days. The delay is an integer of at least 1. The default is 7. The job skips a User who is not yet that old unless it was queued with force. Cleanup runs only while `nightlyTasks.databaseCleanup` is true, which is the default, at `nightlyTasks.startTime`. `GET /api/server/config` includes `userDeleteDelay` as that same number. The delete modal and the restore label read it. The jobs screen that would list this job stays unspecified.
