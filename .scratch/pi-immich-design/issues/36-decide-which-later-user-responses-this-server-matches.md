# Decide which later-user responses this server matches

Type: grilling
Status: resolved

## Question

[Decide how a later User is created](20-decide-how-a-later-user-is-created.md) locks the admin create, the quota, no welcome mail, and web onboarding. [Inventory how the web UI creates a User](27-inventory-how-the-web-ui-creates-a-user.md) names the calls. The web screen a non-admin hits before the library is `PUT /api/users/me` with the new password, then logout, not `POST /api/auth/change-password`. That POST is the settings form, and it requires a new password of at least 8 characters. The PUT accepts any string and clears `shouldChangePassword`. Where the Web UI can see a behavior, match v3.3.6. A difference is allowed when the Pi cannot do it. Which of those calls does this server answer the way v3.3.6 does, and which response changes because the Pi cannot do it?

## Comments

Recommendation accepted: both password calls match v3.3.6. The phone and the settings form stay on `POST /api/auth/change-password`. The web gate before the library is `PUT /api/users/me`.

The remaining calls on this path take the same recommendation. Each response the page reads matches v3.3.6. The one difference is `isOnboarded` on `GET /api/server/config`, which is true from the first start.

## Answer

Every call [Inventory how the web UI creates a User](27-inventory-how-the-web-ui-creates-a-user.md) names matches v3.3.6, except `isOnboarded` on `GET /api/server/config`. That flag is true from the first start. v3.3.6 leaves it false until an admin finishes the server wizard. This server does not run that wizard. The admin and the object-storage location already exist before anyone signs in, from [Decide how the first User is created](10-decide-how-the-first-user-is-created.md). The wizard's storage step asks for a library location this server does not use. No other response on this path changes because of the Pi. Welcome mail stays unsent, and `email: false` stays as [Decide how a later User is created](20-decide-how-a-later-user-is-created.md) already set.

`GET /api/server/config` returns 200. `maintenanceMode` is false. `isInitialized` is true. `isOnboarded` is true. The login page and the root load read those three. The other fields of that document are not read on this path.

`GET /api/public/config` returns 200. `passwordLogin.enabled` is true. `oauth.enabled` is false. `server.loginPageMessage` is `''`, so the login banner stays hidden.

`GET /api/server/features` returns 200. This path reads `email: false` and `oauth: false`. Those two are already decided.

`GET /api/system-config` and `GET /api/system-config/defaults` each return 200 with a JSON object. The user list, the new-user form, and the detail page do not read that object. A thrown call would blank the admin layout, so both calls succeed. The fields other admin screens read stay unspecified.

`GET /api/server/storage` returns 200 and the seven storage fields. `diskSizeRaw`, `diskUseRaw`, and `diskAvailableRaw` are the total, used, and available bytes of the filesystem that holds the thumbnail directory. Used is total minus free. `diskUsagePercentage` is that used portion times 100, to two decimal places. The three human-readable fields are those same byte counts. The new-user form reads `diskSizeRaw` and only warns.

`GET /api/users/me` returns 200 and the admin user document below. The auth load reads `isAdmin`. A missing `license.activatedAt` makes the client call `GET /api/server/about`. This path does not require that call to succeed. `license` is null, and a failed about call is ignored. `GET /api/users/me/preferences` returns 200 and the preferences document below. A missing `cast` throws when the privacy step renders, so `cast` is present.

`POST /api/auth/login` stays 201. The JSON includes the fields [Decide what a session stores](11-decide-what-a-session-stores.md) names, plus `isOnboarded`. A User with no onboarding row is `isOnboarded: false`. After `PUT /api/users/me/onboarding`, the next login sends true. The web checks run in order. An admin while server `isOnboarded` is false would open onboarding. That flag is already true, so this branch does not run. A non-admin with `shouldChangePassword` opens `/auth/change-password` and does not open the library. Otherwise a false `isOnboarded` opens `/auth/onboarding`. Otherwise the page opens `/photos`.

`PUT /api/users/me` on that change-password screen returns 200 and the same admin user document. The body is `{ "password": "<the new password>" }`. A non-empty password is stored as the hash and `shouldChangePassword` becomes false. An empty or missing password leaves the flag set. There is no 8-character minimum and no current-password check. This call does not delete any Session. The page then calls `POST /api/auth/logout` and returns to login. The page reads no field of the PUT body.

`POST /api/auth/change-password` stays the settings form and the phone. It returns 200 and the same admin user document. The body is the current `password`, a `newPassword` of at least 8 characters, and `invalidateSessions`. A wrong current password is 400 with message `Wrong password`. A shorter `newPassword` is 400. Success stores the new hash and clears `shouldChangePassword`. Other Sessions for that User are deleted. The Session that made the call stays. `invalidateSessions` does not change that result: v3.3.6 deletes the other Sessions even when the flag is false or omitted. The settings page stays put and reads no response field. The phone still logs out after success.

The admin user document, from `GET /api/admin/users`, `POST /api/admin/users`, `GET /api/users/me`, and both password updates, carries `id`, `name`, `email`, `profileImagePath`, `avatarColor`, `profileChangedAt`, `shouldChangePassword`, `isAdmin`, `createdAt`, `updatedAt`, `deletedAt`, `oauthId`, `quotaSizeInBytes`, `quotaUsageInBytes`, `status`, `storageLabel`, and `license`. A new User has `profileImagePath` `''`, `deletedAt` null, `oauthId` `''`, `storageLabel` null, `license` null, and `status` `active`. `createdAt`, `updatedAt`, and `profileChangedAt` are timestamps. `quotaUsageInBytes` is the bytes of that User's Originals, and 0 when there are none. `quotaSizeInBytes` is the cap from [Decide how a later User is created](20-decide-how-a-later-user-is-created.md), or null when there is no cap. A stored avatar color is sent through. A null color is the email fallback: the sum of the email's code points, modulo the color list, in this order: `primary`, `pink`, `red`, `yellow`, `blue`, `green`, `purple`, `orange`, `gray`, `amber`. This path does not add a cluster. `clusterGroupId` may be null. The list reads `id`, `name`, `email`, `quotaSizeInBytes`, and `deletedAt`. The detail page also reads `createdAt`, `updatedAt`, `isAdmin`, `quotaUsageInBytes`, and the avatar fields. A missing `avatarColor` throws there. `POST /api/admin/users` returns 201, and the form reads `id`. A non-admin on these admin routes gets 403. `withDeleted` must be `true` or `false`. Any other value is 400. `id`, when sent, is a UUID.

The preferences document is the v3.3.6 default object in `reference/immich/server/src/utils/preferences.ts`. The detail page reads `emailNotifications.enabled` true, `folders.enabled` false, `memories.enabled` true, `people.enabled` true, `ratings.enabled` false, `sharedLinks.enabled` true, `purchase.showSupportBadge` true, `tags.enabled` false, and `cast.gCastEnabled` false. A missing parent throws, so those parents are present, and so is the rest of that default object. The phone's preferences parse also requires it. A new User has no stored patch, so the response is those defaults. `PUT /api/users/me/preferences` during onboarding sends `{ "cast": { "gCastEnabled": <the switch> } }`, merges that onto the stored preferences, and returns 200 with the merged document.

`PUT /api/users/me/onboarding` with `{ "isOnboarded": true }` returns 200 and `{ "isOnboarded": true }`. The page reads no field. It then opens `/photos`. The config-created admin has no onboarding row, so that admin's first web login still opens the user steps (hello, theme, language, privacy, and the mobile-app note). The server steps do not run. The last step, because the caller is an admin, also calls `POST /api/system-metadata/admin-onboarding` with `{ "isOnboarded": true }`. That returns 204 and leaves the server flag true. A later non-admin does not call it. A non-admin who calls it gets 403.

`GET /api/admin/users/{id}/statistics` returns 200 with `images`, `videos`, and `total`. The page reads `images` and `videos`. A User with no assets is 0, 0, and 0. The count is the same default-visibility, not-deleted split v3.3.6 uses when the query omits `isFavorite`, `isTrashed`, and `visibility`.

`GET /api/admin/users/{id}/sessions` returns 200 and an array. A User who has never signed in gets `[]`, and the page draws no devices. Each row has `id`, `createdAt`, `updatedAt`, `deviceType`, `deviceOS`, `appVersion`, `current`, and `isPendingSyncReset`. This admin call does not mark a current Session, so `current` is false on every row. `isPendingSyncReset` is false. There is no `expiresAt`. `deviceType` and `deviceOS` are strings, never null. Both empty draws "unknown". A null `deviceOS` throws. `appVersion` is a string or null. This amends [Decide what a session stores](11-decide-what-a-session-stores.md): a Session also stores those three device strings, `createdAt`, and `updatedAt`. It still does not store the plaintext token, an expiry, a PIN, or anything about OAuth. Login fills the device strings the way v3.3.6 does. `deviceType` is the browser name, else the device type, else the `devicemodel` header, else `''`. `deviceOS` is the OS name, else the `devicetype` header, else `''`. `appVersion` is the version in a `immich-android/`, `immich-ios/`, or legacy `Immich_Android_` / `Immich_iOS_` user agent, and otherwise null. `updatedAt` is the row's last update, set at login.

`GET /api/admin/users/{id}/calendar-heatmap` returns 200 with `from`, `to`, `series`, and `totalCount`. The page reads `from`, `series`, and `totalCount`. Each series item is `date` (`yyyy-mm-dd`) and `count`. The range is one entry per UTC day from `from` through `to`, and `count` is 0 when that day has no upload. `type` `Upload` counts by the asset's `createdAt`. `totalCount` is the sum of `count`. A User with no assets still gets the zero-filled series. A deleted User, or an unknown id, is 400 with message `User not found`.

`GET /api/users/{id}/profile-image` is not called for a new User, because `profileImagePath` is empty. A request for an empty path is 404. A failed image keeps the letter fallback.

## Comments

[Decide which user update, delete, and restore responses this server matches](41-decide-which-user-update-delete-and-restore-responses-this-server-matches.md) reads `userDeleteDelay` on `GET /api/server/config`. That number is `user.deleteDelay`, default 7. A deleted User's sessions list is `[]`, and their upload heatmap is 400 `User not found`.
