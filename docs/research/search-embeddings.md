# Search embeddings

Where the v3.3.6 server stores the vectors that `POST /api/search/smart` reads, for a text `query` and for `queryAssetId`. Read from `reference/immich` at tag `v3.3.6`, commit `587f549f46f1cd1822a06e16dcccecef04ea4565` (`git describe --tags --exact-match HEAD` and `git rev-parse HEAD` both match). This note does not run the server. Both inputs are compared with rows in `smart_search`. The text vector is not a row. It is requested from the ML service when the search runs. The request the app sends, and the `SearchResponseDto` fields it reads, are in `docs/research/ml-results.md`.

## Route

The global prefix is `api` (`reference/immich/server/src/app.common.ts:65`). `SearchController` is `@Controller('search')`. `POST smart` is `searchSmart`. It takes `SmartSearchDto` and returns `this.service.searchSmart(auth, dto)`. The handler sets HTTP 200 (`reference/immich/server/src/controllers/search.controller.ts:26`, `82-91`).

The route is `@Authenticated({ permission: Permission.AssetRead })` and does not set `sharedLink`. The decorator default is `sharedLink: false` (`reference/immich/server/src/middleware/auth.guard.ts:29-31`). `Permission.AssetRead` is `asset.read` (`reference/immich/server/src/enum.ts:144`). A shared-link session hits `authenticate`, which throws `ForbiddenException` before the handler (`reference/immich/server/src/services/auth.service.ts:234-236`). No session, bearer, cookie, or API key throws `UnauthorizedException('Authentication required')` (`auth.service.ts:253-276`). An API key still needs `asset.read`, or the guard throws `ForbiddenException` with `Missing required permission: asset.read` (`auth.service.ts:239-244`). The global filter copies an `HttpException` body, then deletes `error` and `statusCode`, and sends that JSON (`reference/immich/server/src/middleware/global-exception.filter.ts:41-62`, `reference/immich/server/src/app.module.ts:46`). A string exception therefore leaves `{ message: '<the exception string>' }`. Forbidden is 403. Missing authentication is 401.

`query` and `queryAssetId` are both optional. `query` is `z.string().trim()`. `queryAssetId` is a uuid v4. Nothing in the schema requires one of them, and nothing rejects both (`reference/immich/server/src/dtos/search.dto.ts:390-399`). `ZodValidationPipe` runs before the handler (`app.module.ts:47`). A `queryAssetId` that is not a uuid v4 never reaches it. That is `ZodValidationException`, and the filter answers 400 `{ message: 'Validation failed', errors: <zod issues> }` (`global-exception.filter.ts:48-56`). Trimmed whitespace is still a string, so an empty or blank `query` is not that error.

The service checks `query` first, and the check is truthy, so a trimmed empty string is not a query. A non-empty `query` returns the text vector and does not read `queryAssetId`, even when both are set. A blank `query` with `queryAssetId` set uses the asset. When the trimmed `query` is empty and `queryAssetId` is absent, `resolveEmbedding` throws `BadRequestException('Either `query` or `queryAssetId` must be set')` (`reference/immich/server/src/services/search.service.ts:325-353`). That is 400 `{ message: 'Either `query` or `queryAssetId` must be set' }`.

A body with `filter`, `orderBy`, or `cursor` is the v3 search. Any other body is the flat search. The two shapes cannot be mixed (`search.dto.ts:312-315`, `329-352`, `search.service.ts:168-171`). The app omits `filter`, so it stays on the flat method (`docs/research/ml-results.md`).

## Table

Asset vectors for this route are `smart_search`. The primary key is `assetId`, one row per asset. `assetId` is a uuid, not null, and a foreign key to `asset.id` with `ON DELETE CASCADE` (`reference/immich/server/src/schema/tables/smart-search.table.ts:4-14`, `reference/immich/server/src/schema/migrations/1744910873969-InitialMigration.ts:187-188`, `252`, `378`). The migration created the parent as `assets`. A later migration renames that table to `asset` (`reference/immich/server/src/schema/migrations/1752267649968-StandardizeNames.ts:14`, `38-40`). The column is `embedding`, `vector(512)`, not null, storage `EXTERNAL` (`smart-search.table.ts:16-17`, `InitialMigration.ts:187-188`). `synchronize: false` is set on the column and on the index, so that declared length is not what a later model change writes. There is no model-name column and no embedding-type column. The CLIP model name lives in config, `machineLearning.clip.modelName`, default `ViT-B-32__openai` (`reference/immich/server/src/dtos/config.dto.ts:619-630`). `getCLIPModelInfo` maps that name to a dimension. The default model's dimension is 512. Other names in the same map are 640, 768, 1024, 1152, or 1536 (`reference/immich/server/src/constants.ts:67-127`, `reference/immich/server/src/utils/misc.ts:147-162`).

This route does not read `face_search`. That table is a different 512-dimension vector, keyed by `faceId`, and `searchSmart` never joins it (`reference/immich/server/src/schema/tables/face-search.table.ts:4-17`, `reference/immich/server/src/repositories/search.repository.ts:320-336`, `567-585`). `ocr_search` is not a vector table. It stores `text`. The flat builder joins it only when `ocr` is set, and that predicate is a trigram match, not a distance (`reference/immich/server/src/schema/tables/ocr-search.table.ts:4-19`, `reference/immich/server/src/utils/database.ts:517-520`).

## Text query

`resolveEmbedding` does not select a stored text vector. On a cache miss it calls `MachineLearningRepository.encodeText(dto.query, { modelName: machineLearning.clip.modelName, language: dto.language })` (`search.service.ts:330-340`). `encodeText` POSTs to `{url}/predict` and returns the response's `clip` string (`reference/immich/server/src/repositories/machine-learning.repository.ts:14-17`, `43-44`, `162-174`, `211-214`). The search then passes that string into `<=>`. It does not insert it.

The only copy is an in-process `LRUMap` of 100 entries on `SearchService`. The key is `modelName + query + language` (`search.service.ts:36`, `331-339`). An omitted `language` is still concatenated, so the key contains the letters `undefined`. A thrown `encodeText` is not stored. The map is not `smart_search`.

`predict` throws a plain `Error` when every configured URL fails (`machine-learning.repository.ts:165-187`). `ErrorInterceptor` replaces a non-`HttpException` with `InternalServerErrorException`, whose message is `Failed to ` plus the handler name broken on capitals (`reference/immich/server/src/middleware/error.interceptor.ts:24-34`, `reference/immich/server/src/utils/misc.ts:178-179`). The handler name is `searchSmart`, so the message is `Failed to search smart`. The filter then returns 500 `{ message: 'Failed to search smart' }`. The route does not test the returned string. A body whose `clip` value is missing is `undefined`, and that value is what `<=>` receives. There is no 400 for a missing text vector. A database error from that comparison is the same interceptor path, and the same 500 body.

## Query asset

When `query` is empty, `resolveEmbedding` calls `requireAccess` for `Permission.AssetRead` on `queryAssetId`, then `SearchRepository.getEmbedding` (`search.service.ts:343-350`). `getEmbedding` is `selectAll` from `smart_search` where `assetId` equals that id (`search.repository.ts:342-343`). The row's `embedding` string is the vector. No row, or a row whose `embedding` is missing, throws `BadRequestException` with `Asset ${queryAssetId} has no embedding` (`search.service.ts:346-348`). The column is not null, so the practical miss is no row. The status is 400 and the body is `{ message: 'Asset <id> has no embedding' }`.

`requireAccess` throws `BadRequestException('Not found or no asset.read access')` when the id is not in the allowed set (`reference/immich/server/src/utils/access.ts:45-48`). That is 400 `{ message: 'Not found or no asset.read access' }`. Owner access is the viewer's `asset` row, and without an elevated session it also requires `visibility != locked` (`reference/immich/server/src/repositories/access.repository.ts:189-201`). It does not look at `deletedAt` or hidden. Partner access requires the sharing user's `deletedAt` null, the asset's `deletedAt` null, and visibility timeline or hidden (`access.repository.ts:206-228`). Album access requires the asset's `deletedAt` null (`access.repository.ts:148-159`). A missing id, a locked asset without elevation, a partner asset the viewer cannot see, and a trashed asset the viewer does not own all take this same 400. The lookup does not run.

The loaded row is not checked against `machineLearning.clip.modelName`. There is nowhere to check: the table has no model column. A vector written by another CLIP model is used as-is while the row exists. A config change removes those rows, below, and the next `queryAssetId` is the missing-embedding 400 rather than a distinct wrong-model status.

## Ranking

The flat method, which is the one the app calls, is `SearchRepository.searchSmart`. Inside a transaction it runs `set local vchordrq.probes` from the in-memory `probes` entry for `clip_index` (the value starts at 1), inner-joins `smart_search` on `asset.id`, and orders by `smart_search.embedding <=> ${embedding}`, then `asset.id` ascending (`search.repository.ts:320-336`, `reference/immich/server/src/repositories/database.repository.ts:54-56`). The v3 method, `searchSmartV3`, is the same join, the same `<=>` order, and the same probe setting (`search.repository.ts:567-585`). `<=>` is the operator of the `vector_cosine_ops` index. The source does not use an inner-product operator, and this query has no maximum distance. Face search does (`search.repository.ts:356-398`). An asset with no `smart_search` row cannot appear. It is not sorted last.

The index name is `clip_index`. The extension is `DB_VECTOR_EXTENSION` (`pgvector` or `vectorchord`) when that is set, otherwise the first available of VectorChord, then pgvector (`database.repository.ts:34-50`, `reference/immich/server/src/constants.ts:37-41`, `reference/immich/server/src/dtos/env.dto.ts:80`, `reference/immich/server/src/repositories/config.repository.ts:242-250`). VectorChord creates `USING vchordrq (embedding vector_cosine_ops)`. pgvector creates `USING hnsw (embedding vector_cosine_ops) WITH (ef_construction = 300, m = 16)` (`database.ts:1104-1126`). The table decorator also says hnsw, with `synchronize: false`, so that declaration is not what gets created (`smart-search.table.ts:5-10`). The initial migration builds the index with `vectorIndexQuery` (`InitialMigration.ts:519`).

Flat pagination loads `size + 1` rows, drops the extra row, and sets `hasNextPage` from that extra row (`search.repository.ts:332-335`, `reference/immich/server/src/utils/pagination.ts:11-15`). `size` defaults to 100. `page` defaults to 1 (`search.dto.ts:392`, `396`, `search.service.ts:184-185`). `mapResponse` sets `assets.nextPage` to `(page + 1)` as a decimal string when `hasNextPage` is true, otherwise null. `assets.nextCursor` is null. `albums` is zeros and empty arrays. `assets.total` and `assets.count` are the page length (`search.service.ts:197`, `369-384`). The v3 method requests `take: size` and no skip, then discards `hasNextPage`. Its `mapResponse` call sets neither token, so both `nextPage` and `nextCursor` are null even when more rows matched (`search.service.ts:292-299`).

On the flat path the owner list is the viewer plus partners whose `inTimeline` is true, unless `visibility` is locked, in which case it is only the viewer (`search.service.ts:182`, `190`, `356-366`, `reference/immich/server/src/utils/asset.util.ts:119-140`). The builder keeps `asset.ownerId` in that list (`database.ts:491`). Visibility is the requested value, or, when it is omitted and the session is not elevated, `visibility != locked`. An elevated session with no `visibility` adds no visibility predicate (`search.service.ts:173-175`, `193`, `database.ts:434-437`). Locked visibility without elevation throws `UnauthorizedException('Elevated permission is required')` before the search (`search.service.ts:173-175`, `access.ts:412-415`), which is 401 `{ message: 'Elevated permission is required' }`. Trash is excluded: `deletedAt` must be null, unless `withDeleted` is set or the body sets `trashedBefore`, `trashedAfter`, or `isOffline`, which forces `withDeleted` (`database.ts:429`, `547`). The v3 builder has no default `deletedAt` predicate. It always excludes locked assets owned by someone else, and an unelevated session that could match locked gets the same 401 (`database.ts:800-818`, `reference/immich/server/src/utils/search-filter.ts:45-58`). The app's flat body sets visibility to timeline or archive and does not set the trash flags, so the rows that can appear are non-trashed assets owned by the viewer or a timeline partner, with that visibility, and with a `smart_search` row.

## A missing vector

Smart search disabled. `isSmartSearchEnabled` is `machineLearning.enabled && machineLearning.clip.enabled` (`misc.ts:96-98`). Either flag false throws `BadRequestException('Smart search is not enabled')` before `resolveEmbedding`, on both the flat and v3 paths (`search.service.ts:177-180`, `281-285`, `config.dto.ts:619-630`). The status is 400 and the body is `{ message: 'Smart search is not enabled' }`. It is not an empty `SearchResponseDto`. The ML service is not called.

Text embedding call fails, or returns no vector. A thrown `encodeText` or `predict` becomes 500 `{ message: 'Failed to search smart' }`, as above. The body is not a `SearchResponseDto`, so the app does not receive `assets` or `nextPage`. A response that succeeds but has no `clip` string is not turned into that 400, and it is not turned into an empty asset list by this route. It is passed to `<=>`.

Query asset has no embedding. 400 `{ message: 'Asset <id> has no embedding' }`. Not an empty list (`search.service.ts:345-348`).

Query asset id does not exist, or the viewer cannot read it. 400 `{ message: 'Not found or no asset.read access' }` (`access.ts:45-48`). A locked asset without elevation, and a partner or album asset the checks above reject, use this same body. A non-uuid never gets here. It is the validation 400 instead.

`smart_search` is empty, but the query vector exists. The inner join matches nothing. The flat path returns 200 and a `SearchResponseDto` whose `assets.items` is `[]`, `assets.total` and `assets.count` are 0, `assets.facets` is `[]`, `assets.nextPage` is null, and `assets.nextCursor` is null. `albums` is the empty shell (`search.repository.ts:327-335`, `pagination.ts:11-15`, `search.service.ts:197`, `369-384`). The list is empty. It is not an error, and it is not the same assets in another order. Assets that have no row are absent from a non-empty table for the same reason. The v3 path is also 200 with `items` empty and both page tokens null (`search.service.ts:292-299`).

The app treats that empty page and the 400 and 500 bodies the same way on screen. `SearchService.search` returns null when the call throws, and also when `assets.items` is empty (`reference/immich/mobile/lib/domain/services/search.service.dart:14-29`). A new search clears the list first, then searches (`reference/immich/mobile/lib/presentation/pages/search/search.page.dart:79-89`). `PaginatedSearchNotifier.search` leaves the assets already in state when the result is null (`reference/immich/mobile/lib/presentation/pages/search/paginated_search.provider.dart:46-57`). After the clear, that is no hits. A later page that fails keeps the hits already shown. Neither path shows the HTTP `message`.

## Job

The row is written by the job `SmartSearch` on the `smartSearch` queue. The handler is `SmartInfoService.handleEncodeClip` (`reference/immich/server/src/enum.ts:847`, `939-940`, `reference/immich/server/src/services/smart-info.service.ts:87-118`). It loads preview files for the asset (`reference/immich/server/src/repositories/asset-job.repository.ts:222-229`). No asset, or not exactly one preview, returns `failed` and does not write. Visibility hidden returns `skipped` and does not write or delete. Otherwise `encodeImage` returns the `clip` string for `machineLearning.clip.modelName`. If that name changed while the job waited, the handler returns `skipped` and does not write. Otherwise `SearchRepository.upsert` inserts `(assetId, embedding)` or, on `assetId` conflict, replaces `embedding` (`search.repository.ts:480-485`, `smart-info.service.ts:103-116`).

`SmartSearch` is queued from two places. `AssetGenerateThumbnails` `onDone` queues it, with the same job data, when `source` is `upload` or `notify` is set (`reference/immich/server/src/services/job.service.ts:91-92`, `167-188`). Upload metadata keeps `source: 'upload'` through storage-template migration into that thumbnail job (`reference/immich/server/src/services/asset-media.service.ts:187`, `reference/immich/server/src/services/metadata.service.ts:413-417`, `reference/immich/server/src/services/storage-template.service.ts:138-141`, `job.service.ts:119-122`). Showing an asset queues the thumbnail job with `notify: true` (`reference/immich/server/src/services/notification.service.ts:146-148`). `SmartSearchQueueAll` queues one `SmartSearch` per asset from `streamForEncodeClip` (`smart-info.service.ts:67-84`). That stream is non-hidden, non-trashed assets that have a preview, and, unless `force` is set, assets that have no `smart_search` row (`asset-job.repository.ts:180-219`). Starting the `smartSearch` queue is what queues `SmartSearchQueueAll` (`reference/immich/server/src/services/queue.service.ts:212-213`). Nightly jobs do not queue it (`queue.service.ts:267-299`). `onDone` runs only after `success` or `skipped` (`job.service.ts:91-92`), so a failed thumbnail job does not queue the write.

Deleting the `asset` row removes the embedding. `smart_search_assetId_fkey` is `ON DELETE CASCADE` (`smart-search.table.ts:13`, `InitialMigration.ts:378`). `AssetDelete` calls `assetRepository.remove`, which is `DELETE FROM asset` (`reference/immich/server/src/services/asset.service.ts:314-346`, `reference/immich/server/src/repositories/asset.repository.ts:656-657`). A library unlink does the same delete (`reference/immich/server/src/services/library.service.ts:688-696`). `UserDelete` deletes the `user` row (`reference/immich/server/src/services/user.service.ts:262-293`, `reference/immich/server/src/repositories/user.repository.ts:225-228`), and `asset.ownerId` is `ON DELETE CASCADE` (`reference/immich/server/src/schema/tables/asset.table.ts:74-75`), so those embeddings go with the assets. Trashing does not delete the row. It sets `asset.deletedAt` (`asset.service.ts:384-395`). Hiding does not delete it either. The encode job skips a hidden asset and leaves an existing row (`smart-info.service.ts:99-101`).

A CLIP model change deletes every row and does not queue a rewrite. Same dimension, different model name: `TRUNCATE smart_search` (`smart-info.service.ts:44-60`, `reference/immich/server/src/repositories/database.repository.ts:359-360`). A dimension change, including `SmartSearchQueueAll` with `force`, `DELETE`s every row and alters `embedding` to `vector(<dimSize>)` before the queue-all streams assets again (`smart-info.service.ts:51-57`, `74-78`, `database.repository.ts:322-356`). After either delete, a `queryAssetId` is the missing-embedding 400, and a text query against an empty table is the empty 200 page above.
