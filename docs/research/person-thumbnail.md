# Person thumbnail

Where the v3.3.6 server stores the file that `GET /api/people/{id}/thumbnail` reads. Read from `reference/immich` at tag `v3.3.6`, commit `587f549f46f1cd1822a06e16dcccecef04ea4565` (`git describe --tags --exact-match HEAD` and `git rev-parse HEAD` both match). This note does not run the server.

## Route

The global prefix is `api` (`reference/immich/server/src/app.common.ts:65`). `PersonController` is `@Controller('people')`. `GET :id/thumbnail` is `getPersonThumbnail`. The id is `UUIDParamDto`, a uuid v4. The handler declares no query object. It calls `sendFile` with `PersonService.getThumbnail(auth, id)` (`reference/immich/server/src/controllers/person.controller.ts:46`, `164-178`, `reference/immich/server/src/validation.ts:97-101`). The route is `@Authenticated({ permission: Permission.PersonRead })` and does not set `sharedLink`. The decorator default is `sharedLink: false` (`reference/immich/server/src/middleware/auth.guard.ts:29-31`, `reference/immich/server/src/enum.ts:247`). A shared-link session hits `authenticate`, which throws `ForbiddenException` before the handler (`reference/immich/server/src/services/auth.service.ts:234-236`). The global filter returns that exception's status, 403 (`reference/immich/server/src/middleware/global-exception.filter.ts:41-44`). An API key on this route still needs `person.read` (`auth.service.ts:239-244`).

`getThumbnail` calls `requirePersonAccess` for `{ personGroupId: id, ownerId: auth.user.id }` and `Permission.PersonRead`. The check passes when that user owns a `person` row for the group, or when `person_user` has `sharedWithId` and `sharedById` both equal to that same user id and a read, write, or admin role. Anything else throws `BadRequestException` (`reference/immich/server/src/services/person.service.ts:207-212`, `reference/immich/server/src/utils/access.ts:52-63`, `75-77`, `reference/immich/server/src/repositories/access.repository.ts:540-570`). A missing person is that exception. It is thrown inside the `sendFile` callback. `sendFile` does not rethrow it. Every error from the callback or from the disk read becomes `next(new NotFoundException())` (`reference/immich/server/src/utils/file.ts:57-78`). The filter returns 404 (`global-exception.filter.ts:41-44`).

The service then loads `PersonRepository.getForThumbnail`. No row, or a path that is `''` or SQL null, throws `NotFoundException` (`person.service.ts:213-217`, `reference/immich/server/src/repositories/person.repository.ts:605-630`). That is also rewritten by `sendFile` to 404. There is no placeholder image and no other route. The request shape the app sends is in `docs/research/ml-results.md`.

## Column

The path is `person.thumbnailPath`. The table is `person`. The primary key is `(ownerId, personGroupId)`. The column defaults to `''` and is not nullable. `faceAssetId` is a nullable foreign key to `asset_face.id` and is not a path (`reference/immich/server/src/schema/tables/person.table.ts:19`, `40-54`, `62-66`, `74-75`). `asset_face` stores the bounding box and dimensions. It has no file column (`reference/immich/server/src/schema/tables/asset-face.table.ts:50-88`).

`getForThumbnail` does not call `getPersonThumbnailPath`. It reads two scalars from `person_group` where `id` is the URL id. `thumbnailPath` is the viewer's own `person.thumbnailPath` (`ownerId` equals the viewer). `sharedThumbnailPath` is one other `person.thumbnailPath` in that group, joined through `person_user` with `sharedWithId` equal to the viewer and `thumbnailPath != ''`, `limit 1`, no `ORDER BY` (`person.repository.ts:605-630`). The service opens `thumbnailPath || sharedThumbnailPath` (`person.service.ts:214-222`). An empty own path falls through to the shared path. A non-empty own path is opened even when that file is gone. It does not fall through. A second owner in the group changes the opened file only in that fall-through. While the viewer's path is non-empty, the GET opens the viewer's file.

`sendFile` checks `access(path, R_OK)` and then `res.sendFile` on that same string (`file.ts:54-73`). It does not prefix the media location. The response `Content-Type` is `mimeTypes.lookup(path)`. A path ending in `.jpeg` is `image/jpeg` (`person.service.ts:219-222`, `reference/immich/server/src/utils/mime-types.ts:47`, `150-151`). `Cache-Control` is `private, no-cache, no-transform` (`file.ts:40-44`, `62-65`, `reference/immich/server/src/enum.ts:651-654`).

The writer stores an absolute path, below. The column is still a string. A group-id change does not recompute it. `mergePeople`, when the owner already has a row in the target group, copies name and birth date onto that row, reassigns the source faces, and deletes the source person (`person.service.ts:711-724`). Delete unlinks the source `thumbnailPath` (`person.service.ts:332-339`, `reference/immich/server/src/repositories/storage.repository.ts:166-175`). The target column is unchanged, so the GET for the target id still opens the target file. When the owner has no target row, `updateGroupId` sets `person.personGroupId` to the new id and does not set `thumbnailPath` (`person.repository.ts:207-225`). The GET for the new id opens the old absolute path. The formula path for the new group id is a different file, and this GET does not open it.

Face reassignment updates `asset_face.personGroupId`. It does not change `thumbnailPath` by itself (`person.service.ts:107-128`, `132-147`, `person.repository.ts:192-203`). It queues a new thumbnail only in the cases under Jobs. `docs/research/rendition-files.md` states the person file as the `getPersonThumbnailPath` formula and as this GET. The formula is what the writer returns. This GET opens the column. After `PersonGenerateThumbnail` or `PersonFileMigration` those are the same path. After `updateGroupId` they are not.

There is no second face image. `PersonPathType.Face` is the migration path type for this same column (`reference/immich/server/src/enum.ts:488-490`, `reference/immich/server/src/cores/storage.core.ts:183-195`, `340-346`). No job writes a per-face file.

## Directory

`StorageCore.getPersonThumbnailPath` is `getNestedPath(StorageFolder.Thumbnails, ownerId, personGroupId + '.jpeg')` (`storage.core.ts:120-121`). `StorageFolder.Thumbnails` is `thumbs` (`enum.ts:362-368`). `getBaseFolder` joins the media location and that folder. `getNestedFolder` adds `ownerId`, then `filename.slice(0, 2)` and `filename.slice(2, 4)`. `getNestedPath` joins the filename (`storage.core.ts:108-117`, `356-361`). The filename is `{personGroupId}.jpeg`, so the absolute path is `{mediaLocation}/thumbs/{ownerId}/{personGroupId[0:2]}/{personGroupId[2:4]}/{personGroupId}.jpeg`. The id in the name is the person group id, not a face id. The extension is fixed `.jpeg`. It is not `image.thumbnail.format`.

The media location is set once at bootstrap. `IMMICH_MEDIA_LOCATION`, when set, must match `^/` (`reference/immich/server/src/dtos/env.dto.ts:15`, `52`, `reference/immich/server/src/repositories/config.repository.ts:356-358`). Unset, `detectMediaLocation` uses `/data` or `/usr/src/app/upload` when exactly one of those directories exists, and otherwise `/usr/src/app/upload` (`reference/immich/server/src/services/storage.service.ts:23-44`). Bootstrap stores that choice on `StorageCore` and in system metadata under `MediaLocation` (`storage.service.ts:46-48`, `99-133`, `enum.ts:373-374`). There is no second join at request time. `handleGeneratePersonThumbnail` stores `getPersonThumbnailPath` as returned (`reference/immich/server/src/services/media.service.ts:425-426`, `449-450`). An older migration rewrote a relative `upload/...` prefix on `person.thumbnailPath` to `/usr/src/app/upload/...` when `IMMICH_MEDIA_LOCATION` was unset (`reference/immich/server/src/schema/migrations/1752759108283-ConvertToAbsolutePaths.ts:6-26`). A later media-location change rewrites the stored prefix with `REGEXP_REPLACE` (`reference/immich/server/src/repositories/database.repository.ts:418-449`). Current writers do not store a relative path.

## Job

One job writes the file. The name is `PersonGenerateThumbnail` (`enum.ts:929`). The queue is `thumbnailGeneration` (`enum.ts:842`). The handler is `MediaService.handleGeneratePersonThumbnail` (`media.service.ts:391-395`). The job options set priority `1` and no deduplication id (`reference/immich/server/src/repositories/job.repository.ts:268-269`).

`getDataForThumbnailGenerationJob` inner-joins `person.faceAssetId` to `asset_face` and then to `asset`, and skips a face with `deletedAt` set. It selects the face box, the face's `imageWidth` and `imageHeight`, `asset.type`, `asset.originalPath`, and the non-edited preview path (`person.repository.ts:557-579`, `reference/immich/server/src/utils/database.ts:235-241`). No row: the handler logs and returns `failed`. It does not write (`media.service.ts:397-400`). A video uses the preview path. A missing preview returns `failed` and writes nothing (`media.service.ts:405-410`). Any other asset type uses `originalPath`, unless `image.extractEmbedded` is on and `mimeTypes.isRaw(originalPath)`. The default `extractEmbedded` is false. In that raw case it extracts an embedded image and, when the extract is kept, decodes that buffer instead of the Original (`media.service.ts:411-416`, `233-239`, `reference/immich/server/src/dtos/config.dto.ts:709`). It does not open the asset thumbnail file, the encoded video, or an edited preview.

The crop is the face box, clamped to the face's stored image size, scaled onto the decoded image, expanded by `1.1`, and squared (`media.service.ts:435-446`, `455-489`). `generateThumbnail` runs sharp `extract`, resizes with fit `outside` and `withoutEnlargement`, and calls `toFile` on the final path (`reference/immich/server/src/repositories/media.repository.ts:160-167`, `181-190`, `218-224`). Format is `ImageFormat.Jpeg`, which is `jpeg`. Size is `FACE_THUMBNAIL_SIZE`, `250`. Quality is `image.thumbnail.quality`, default `80`. Progressive is false. Colorspace is `image.colorspace`, default `p3` (`media.service.ts:428-447`, `reference/immich/server/src/constants.ts:65`, `enum.ts:593-603`, `config.dto.ts:695-709`). Quality at least `80` sets chroma subsampling `4:4:4` (`media.repository.ts:184-188`). The handler then `personRepository.update`s `thumbnailPath` to that formula path (`media.service.ts:449-450`). `toFile` overwrites the same path. The handler does not read the previous `thumbnailPath` and does not queue `FileDelete`. A previous path that is not the formula path is left on disk. `onDone` of this job sends the websocket event `on_person_thumbnail`. It queues no other job (`reference/immich/server/src/services/job.service.ts:126-129`).

A person with no usable face is not given a file. `createNewFeaturePhoto` calls `getRandomFace`, which selects the first visible, non-deleted `asset_face` for that `personGroupId` and has no `ORDER BY`. No row: it does not queue the job (`person.service.ts:162-176`, `person.repository.ts:922-929`). The thumbnail queue does the same before it queues: no `faceAssetId` and no face means that person is skipped (`media.service.ts:90-103`). `PersonCleanup` does not write a thumbnail. It loads `getAllWithoutFaces` and deletes those people, which unlinks each `thumbnailPath` (`person.service.ts:343-347`, `332-339`). That query left-joins `asset_face` on `personGroupId` only, keeps `deletedAt` null and `isVisible` null or true, and returns groups whose `count(asset_face.assetId)` is 0 (`person.repository.ts:497-506`). A person with no face row matches. A person whose faces are all deleted or all hidden does not: the `WHERE` drops those joined rows, so the person is absent rather than counted as zero. A visible face on the same group from any owner keeps the row.

The job is queued from these places.

- `handleRecognizeFaces`, after it inserts a new `person` with `faceAssetId` set to that face. An existing person for the owner and group is not queued (`person.service.ts:616-626`). That handler runs from `FacialRecognition` jobs. `handleDetectFaces` queues those for each new machine-learning face, and does not queue `PersonGenerateThumbnail` itself (`person.service.ts:454-457`). `AssetGenerateThumbnails` `onDone` queues `AssetDetectFaces` when `source` is `upload` or `notify` is set (`job.service.ts:167-181`). Both face handlers return `skipped` when facial recognition is disabled (`person.service.ts:384-387`, `544-547`). The default is enabled unless `IMMICH_MACHINE_LEARNING_ENABLED` is `false` (`config.dto.ts:619-620`, `635-636`, `reference/immich/server/src/utils/misc.ts:101-102`).
- `createNewFeaturePhoto`, after it sets `faceAssetId`. Callers are `reassignFaces` and `reassignFacesById`, when the destination `faceAssetId` is null or the moved face was the source person's featured face, and `createFace` when the person has no featured face (`person.service.ts:114-127`, `143-147`, `819-820`).
- `update`, when `featureFaceAssetId` is set. The face must belong to the group and the asset must be readable. The update stores that face id, then the job is queued (`person.service.ts:263-288`).
- `handleQueueGenerateThumbnails`, the handler for `AssetGenerateThumbnailsQueueAll`. With `force` false or omitted it streams people whose `thumbnailPath` is `''`. With `force` true it streams every person. It sets `faceAssetId` from `getRandomFace` when that column is null, then queues this job (`media.service.ts:68-107`, `person.repository.ts:324-329`). Nightly `missingThumbnails`, default true, queues that queue-all with `force: false` (`config.dto.ts:721-727`, `reference/immich/server/src/services/queue.service.ts:291-293`). Starting the `thumbnailGeneration` queue manually queues the same queue-all with the command's `force` (`queue.service.ts:228-229`, `reference/immich/server/src/dtos/queue.dto.ts:15`).
- `applyTaggedFaces`, during metadata extraction, when `metadata.faces.import` is on. The default is false (`reference/immich/server/src/services/metadata.service.ts:401-402`, `misc.ts:105`, `config.dto.ts:658-661`). It queues the job after inserting the person and before `updateAll` sets `faceAssetId` (`metadata.service.ts:968-1000`). The thumbnail query inner-joins `faceAssetId`, so a run that starts before that update finds no row and returns `failed`.

Nightly `databaseCleanup`, default true, queues `PersonCleanup`, which deletes and unlinks. It does not generate (`queue.service.ts:271-275`, `config.dto.ts:722`). The manual job of that name is the same (`job.service.ts:17-18`). Nightly `clusterNewFaces`, default true, queues `FacialRecognitionQueueAll` with `nightly: true`, which can create a person and then queue `PersonGenerateThumbnail` (`queue.service.ts:295-297`, `config.dto.ts:727`, `person.service.ts:484-507`, `616-626`). `AssetDetectFacesQueueAll` calls `handlePersonCleanup` inline when `force` is true, and queues `PersonCleanup` when `force` is omitted (`person.service.ts:364-377`). Neither of those writes the thumbnail file.

Changing the featured face queues the job as above. The new run crops the new `faceAssetId` and `toFile`s the same formula path for that owner and group. The column is set to that path. The previous bytes are overwritten. They are not unlinked as a separate file.

A path that no longer matches the formula is moved by `PersonFileMigration`, not by the thumbnail job. `FileMigrationQueueAll` queues it for every person (`media.service.ts:126-132`). The handler calls `movePersonFile` with `PersonPathType.Face` (`person.service.ts:636-643`). `moveFile` returns immediately when `thumbnailPath` is empty or already equal to `getPersonThumbnailPath`. Otherwise it renames the old file onto the formula path, or copies and unlinks across devices, then updates `person.thumbnailPath` (`storage.core.ts:183-202`, `241-272`, `340-346`). Merge does not queue either job. `updateGroupId` leaves the old path in the column until one of those two jobs runs.

## A missing file

A null or empty path is `NotFoundException` from `getThumbnail`, and `sendFile` turns that into 404. A path that is not readable fails `access`, which is not an `HttpException`, and `sendFile` also turns that into 404 (`file.ts:57-78`, `reference/immich/server/src/utils/logger.ts:16-21`). The handler does not send a placeholder. The same 404 is what a missing person becomes, because `sendFile` replaces the `BadRequestException` before the filter sees it. A shared link never reaches that code. It is 403 from the guard.
