# Upload and checksum

Which HTTP calls the official mobile app makes to decide a photo or video is already on the server, and to upload one. Read from `reference/immich` at tag `v3.3.6`, commit `587f549f46f1cd1822a06e16dcccecef04ea4565` (`git describe --tags --exact-match HEAD`).

The generated Dart client is not in the checkout. The upload itself is not a generated call. It is a hand-built `POST` to `{serverEndpoint}/assets`, and `serverEndpoint` is the client `basePath`, a URL that already ends in `/api` (`reference/immich/mobile/lib/services/api.service.dart:115-119`, `reference/immich/open-api/immich-openapi-specs.json:18391-18394`). That is `POST /api/assets`. The spec operation is `uploadAsset` (`immich-openapi-specs.json:3780-3782`). Nest mounts it on controller route `assets` under the global prefix `api` (`reference/immich/server/src/enum.ts:647`, `reference/immich/server/src/app.common.ts:65`, `reference/immich/server/src/controllers/asset-media.controller.ts:44-51`).

The app does not ask the server "do you have this checksum?" before sending bytes. `POST /api/assets/bulk-upload-check` exists. No call to `checkBulkUpload`, `bulk-upload-check`, or the header `x-immich-checksum` was found under `mobile/lib`, `mobile/android`, or `mobile/ios`.

## Sequence

**Already on the server, before any upload HTTP.** Backup candidates are local assets in an album marked selected, not also in an album marked excluded, whose `checksum` is not null, and whose `checksum` is not equal to any `remote_asset_entity.checksum` owned by this user (`reference/immich/mobile/lib/infrastructure/repositories/backup.repository.dart:82-113`). The remote row's owner is the only user filter. A partner row with the same checksum does not count. `deletedAt` is not filtered, so a trashed remote asset still counts. `libraryId` is not filtered. A null checksum is "processing" and is not a candidate (`backup.repository.dart:36-42`, `109-111`). Those remote checksums are strings already stored from sync (`reference/immich/mobile/lib/infrastructure/repositories/sync_stream.repository.dart:243`, `283`). The server sends them as base64 (`reference/immich/server/src/services/sync.service.ts:34-36`). This query is the skip. A matching row means no file is opened and `POST /api/assets` is not called.

The checksum string is a base64 SHA-1 written by the native hasher, not by the upload request. Hashing runs over assets in backup albums whose local checksum is still null (`reference/immich/mobile/lib/domain/services/hash.service.dart:40-58`, `86-117`, `reference/immich/mobile/lib/infrastructure/repositories/local_album.repository.dart:246-251`). iOS background backup and the Android background worker both sync remote assets before a new backup batch (`reference/immich/mobile/lib/domain/services/background_worker.service.dart:149-161`, `196-201`). A foreground backup tap does not itself call sync first (`reference/immich/mobile/lib/providers/backup/backup.provider.dart:124-149`). Until a remote row exists, the same bytes are still a candidate. The upload success path does not insert that row, except the album-add stub below.

**Photo, one `POST /api/assets`.** Foreground backup (the in-app button, both platforms) and the Android background worker load candidates and call `uploadSingleAsset` (`foreground_upload.service.dart:86-113`, `background_worker.service.dart:300-307`). Android background is sequential; the button uses three workers. If `getLocalAsset` already has a `remoteId`, the HTTP upload is skipped and the success path runs anyway (`foreground_upload.service.dart:258-261`). `remoteId` is the current user's remote asset with the same checksum (`reference/immich/mobile/lib/infrastructure/repositories/local_asset.repository.dart:28-48`). Otherwise the app reads `photo_manager`'s `originFile` (`reference/immich/mobile/lib/infrastructure/repositories/storage.repository.dart:15-21`), or, on iOS when that file is not local, `loadFile` (`storage.repository.dart:90-113`, `foreground_upload.service.dart:270-298`). The filename is the Photos title with the extension of the file actually opened (`foreground_upload.service.dart:320-323`, `asset_media.repository.dart:80-91`). One multipart `POST`. Status 200 and 201 are both success when the JSON has a string `id`. The app does not read `status`. It does not upload again for that attempt. Wi-Fi-only assets are skipped for this run and stay candidates (`foreground_upload.service.dart:107-110`, `467-475`).

**Video, the same `POST`.** A video is one asset and one body. The only request difference on the foreground path is `duration`, the asset's `durationMs` (`foreground_upload.service.dart:333`). Cellular permission is the video switch, not the photo switch (`foreground_upload.service.dart:467-470`). The hasher reads a video resource, not an image resource (`reference/immich/mobile/ios/Runner/Sync/PHAssetExtensions.swift:78-86`).

**Live photo, two `POST`s.** `AssetEntity.isLivePhoto` uploads the motion file first, field `visibility` `hidden`, then the still with `livePhotoVideoId` set to the motion response `id` (`foreground_upload.service.dart:336-360`). The unit test expects that visibility string to be `hidden` (`reference/immich/mobile/test/services/foreground_upload.service_test.dart:109-130`). The still is the asset whose checksum the candidate query used. The paired video is not what the hasher reads: iOS `getResource` keeps photo resources for an image (`PHAssetExtensions.swift:78-81`). If the motion `POST` fails, the foreground path still uploads the still with no `livePhotoVideoId` and does not report the motion error (`foreground_upload.service.dart:354-360`). If the motion file is missing, it reports an error and still uploads the still (`foreground_upload.service.dart:305-311`). iOS background backup is different: it enqueues only the motion file first (at most 100 candidates), and enqueues the still only after that task completes with a body `id` (`background_upload.service.dart:163-176`, `219-246`, `294-331`). A missing motion file drops the asset (`background_upload.service.dart:300-302`). A duplicate motion response is not special: any body with `id` is enough to enqueue the still.

**iOS background backup** does not use `uploadFile`. It enqueues `background_downloader` `UploadTask`s, `POST`, multipart field `assetData`, `retries: 3` (`background_upload.service.dart:391-455`). On `TaskStatus.complete` it parses `id` for the live-photo follow-up and for stacking (`background_upload.service.dart:199-216`). `duration` is the string `0`, not the asset duration (`background_upload.service.dart:421`). The foreground service's one-shot transport retry is not this path.

**Manual upload** is the same `uploadSingleAsset` path, for a caller-supplied list rather than backup candidates (`foreground_upload.service.dart:141-156`). The timeline action only offers assets that are not merged, meaning no `remoteId` (`reference/immich/mobile/lib/presentation/actions/upload.action.dart:15-17`, `reference/immich/mobile/lib/utils/asset_filter.dart:19`, `reference/immich/mobile/lib/domain/models/asset/base_asset.model.dart:64`). An asset that was never in a backup album can have a null checksum and still be uploaded. **Share intent** does not hash and does not look up a remote id. `deviceAssetId` is `p.hash` of the path string, timestamps come from `file.stat`, `duration` is `0` (`foreground_upload.service.dart:158-188`, `431-461`). **Adding locals to an album** skips upload when `remoteId` is already set and only uploads the rest, then `PUT /api/albums/{id}/assets` (`reference/immich/mobile/lib/domain/services/remote_album.service.dart:36-51`, `235-257`).

**After a 200 or 201.** Nothing in the client reads `duplicate` versus `created`. The bytes were already sent, unless the local query skipped the `POST`. The server, not the app, refuses a second row. On success the app may `POST /api/stacks` to pair this upload with the previous checksum's remote asset. That is the edited-file path, not the duplicate path. A foreground quota error (`Quota has been exceeded!`) stops the rest of the run (`foreground_upload.service.dart:403-405`).

## Calls

### `POST /api/assets`

- When: every photo, video, live-photo half, manual upload, and share-intent file that was not skipped by the local checksum join or by an existing `remoteId`. Not called for a backup candidate the local query already matched. iOS background uses the same path via `UploadTask`. One call per file. A live photo is two calls, motion video then still.
- Method and path: `POST /api/assets`. No query. The spec also allows shared-link query `key` and `slug` (`immich-openapi-specs.json:3783-3799`). This app does not add them (`reference/immich/mobile/lib/repositories/upload.repository.dart:71-74`, `background_upload.service.dart:408-409`).
- Request: `multipart/form-data`. File part name `assetData` (`upload.repository.dart:79`, `background_upload.service.dart:448`). Text fields the app sets: `deviceAssetId` (local id, or for share intent the path hash), `deviceId` (store id), `fileCreatedAt`, `fileModifiedAt` (UTC ISO-8601), `isFavorite` (`true` or `false`), `duration` (foreground: `durationMs` or `0`; background and share intent: `0`), and `filename` on the background task (foreground puts the name on the file part). Live-photo motion adds `visibility` `hidden`. The still adds `livePhotoVideoId` when the motion call returned an id. iOS, and only when `cloudId` is set, and not on the motion part, adds `metadata`: a JSON array of one object `{ "key": "mobile-app", "value": { "iCloudId", "createdAt", "adjustmentTime", "latitude", "longitude" } }` (`foreground_upload.service.dart:326-377`, `background_upload.service.dart:413-435`, `reference/immich/mobile/lib/domain/models/asset/asset_metadata.model.dart:8-52`). No `sidecarData` part. No checksum field. No `x-immich-checksum` header. `deviceAssetId` and `deviceId` are not in `AssetMediaCreateDto` (`immich-openapi-specs.json:20820-20881`). The server dropped those columns (`reference/immich/server/src/schema/migrations/1776263790468-DropDeviceIdAndDeviceAssetId.ts:4-5`). The app still sends them (`foreground_upload.service.dart:327-329`). Headers the app adds beyond the session cookie: foreground uses the shared native client, so `User-Agent` (`immich-android/<version>` or `immich-ios/<version>`), saved custom headers, and `Cookie` (`reference/immich/mobile/android/app/src/main/kotlin/app/alextran/immich/core/HttpClientManager.kt:56`, `362-373`; `reference/immich/mobile/ios/Runner/Core/URLSessionManager.swift:54-57`, `147-156`). The `MultipartRequest` itself sets no extra headers (`upload.repository.dart:71-80`). `deviceModel` and `deviceType` are default headers on the generated client only (`api.service.dart:155-169`); this `POST` does not go through that client. Android adds `Authorization: Basic` only when the server URL contains userinfo (`HttpClientManager.kt:370-372`). iOS background tasks pass only the saved custom headers (`background_upload.service.dart:410-443`); the background session also gets the shared cookie store and `User-Agent` (`URLSessionManager.swift:161-201`).
- Response fields the app requires: JSON `id` as a string, and HTTP 200 or 201 (`upload.repository.dart:97-120`). It does not read `status`. The server uses 200 when `status` is `duplicate` and 201 when `status` is `created` (`asset-media.controller.ts:61-89`). Both bodies are `{ status, id }` (`reference/immich/server/src/dtos/asset-media-response.dto.ts:4-16`, `immich-openapi-specs.json:20884-20918`). A 200 duplicate and a 201 create are the same success. The app does not then skip a second upload of that file; it already finished the one `POST`. It does not retry a finished HTTP response. Status 413 becomes the message `Error(413) File is too large to upload` and is not resent (`upload.repository.dart:100-103`). Any other status outside 200 and 201 is an error. The message is JSON `message` or `error`, else the raw body (`upload.repository.dart:105-114`). `Quota has been exceeded!` is that message and aborts the foreground run (`reference/immich/server/src/services/asset-media.service.ts:368-371`, `foreground_upload.service.dart:403-405`). A body that is not JSON, or an `id` that is not a string, is `Failed to parse server response` and is not resent. A `ClientException` before any response is sent again once; a second transport failure is an error; an abort is cancelled and is not resent (`upload.repository.dart:83-93`, `123-125`; `reference/immich/mobile/test/repositories/upload_repository_test.dart:70-125`). iOS background sets `retries: 3` on the task (`background_upload.service.dart:454`). The downloader package is not in this tree, so this note does not claim which status codes those three retries cover. The server's duplicate is not a 4xx. It is 200 with the existing id, after the unique index `UQ_assets_owner_checksum` rejects the insert (`reference/immich/server/src/utils/database.ts:102-106`, `asset-media.service.ts:197-216`). That index is `(ownerId, checksum)` where `libraryId` is null (`reference/immich/server/src/schema/tables/asset.table.ts:37-43`). The new file is queued for deletion. The existing row is kept. Quota is checked only after the file is on disk and before the insert (`asset-media.service.ts:140-149`). A repeat upload that the app did not skip locally can therefore 400 for quota instead of 200 duplicate, because this app never sends `x-immich-checksum`. That header is what returns 200 before multer runs (`reference/immich/server/src/middleware/asset-upload.interceptor.ts:14-24`).
- Source: `upload.repository.dart:60-130`, `foreground_upload.service.dart:245-419`, `background_upload.service.dart:275-455`. Server: `asset-media.controller.ts:51-90`, `asset-media.service.ts:125-227`, `reference/immich/server/src/middleware/file-upload.interceptor.ts:97-144`. Schema: `immich-openapi-specs.json:3780`, `20820`.

### `GET /api/assets/{id}`

- When: only inside `stackEditedUpload`, and only when the local asset's checksum is null. A manual or album upload that was never hashed. Not used to decide whether to upload. Not used on the share-intent path, which never stacks. Backup of a hashed asset does not need it (`reference/immich/mobile/lib/domain/services/asset.service.dart:201-203`).
- Method and path: `GET /api/assets/{id}` (`getAssetInfo`). Authenticated. No query from this caller.
- Request: no body. The repository reads the whole asset DTO only to return `.checksum` (`reference/immich/mobile/lib/repositories/asset_api.repository.dart:69-70`).
- Response fields the app requires: `checksum`, a string. The server puts base64 SHA-1 there (`reference/immich/server/src/dtos/asset-response.dto.ts:236`, schema description `Base64 encoded SHA1 hash`, `immich-openapi-specs.json:21196-21199`). A null body throws in `checkNull`. The app does not read `status`, `duplicateId`, or `isEdited` here. The value is stored as `previousChecksum` even if the stack call fails (`asset.service.dart:210-212`).
- Source: `asset_api.repository.dart:69-70`, `asset.service.dart:201-213`. Server: `reference/immich/server/src/controllers/asset.controller.ts:92-100`. Schema: `immich-openapi-specs.json:4283`.

### `POST /api/stacks`

- When: after an upload the app treats as success (including a skipped upload that already had `remoteId`), and after an iOS background task completes, and only when `previousChecksum` matches a different remote asset owned by the logged-in user (`asset.service.dart:201-209`, `local_asset.repository.dart:242-255`, `foreground_upload.service.dart:422-428`, `background_upload.service.dart:252-268`). Not called for a first-time backup with no previous checksum. Not called when that previous remote id is the id just returned. A failed stack does not fail the upload (`foreground_upload.service.dart:424-428`). The background handler swallows the error (`background_upload.service.dart:269-271`).
- Method and path: `POST /api/stacks`.
- Request: JSON `{ "assetIds": [newRemoteId, previousRemoteId] }`. First id is the primary (`reference/immich/server/src/dtos/stack.dto.ts:13-17`). `Content-Type: application/json` from the generated client. Session cookie, as on other generated calls.
- Response fields the app requires: the call's return value is discarded after `checkNull` (`asset_api.repository.dart:45-48`). A throw is logged and the upload still counts. The app then writes `previousChecksum` to the checksum it just uploaded, or to the checksum it just fetched (`asset.service.dart:210-212`).
- Source: `asset.service.dart:201-213`, `asset_api.repository.dart:45-48`. Server: `reference/immich/server/src/controllers/stack.controller.ts:28-37`. Schema: `immich-openapi-specs.json:14521`, `29262`.

### `PUT /api/albums/{id}/assets`

- When: album add of a local asset, after `uploadManual` reports success. Not part of backup. Assets that already have `remoteId` skip upload and are added with that id (`remote_album.service.dart:36-51`, `235-257`).
- Method and path: `PUT /api/albums/{id}/assets`.
- Request: JSON `BulkIdsDto` `{ "ids": [remoteId] }` (`album_api_repository.dart:51-58`).
- Response fields the app requires: each item's `success` and `id`. `success` true is added. `error` of `duplicate` is not a failure and is not added again (`album_api_repository.dart:61-66`). Other failures are counted failed and not inserted locally. On add, the app inserts a local remote-asset stub. If the local checksum is null, that stub's checksum is the remote id string, not a hash (`reference/immich/mobile/lib/infrastructure/repositories/remote_album.repository.dart:307-334`). Sync is what later overwrites it.
- Source: `album_api_repository.dart:51-69`, `remote_album.service.dart:270-284`. Server: `reference/immich/server/src/controllers/album.controller.ts:113-125`. Schema: `immich-openapi-specs.json:2629`.

## Checksum

Algorithm is SHA-1 of file bytes, encoded as standard base64 (20 bytes, length 28, padding included).

The phone hasher does not hash the filename, the path, or a sidecar. Android: `MessageDigest` `SHA-1` over the original `MediaStore` stream (`MediaStore.setRequireOriginal` on API 29+), then `Base64.NO_WRAP` (`reference/immich/mobile/android/app/src/main/kotlin/app/alextran/immich/sync/MessagesImplBase.kt:447-484`). iOS: `Insecure.SHA1` over `PHAssetResource` bytes, then `base64EncodedString` (`reference/immich/mobile/ios/Runner/Sync/MessagesImpl.swift:384-426`). The resource is the only media resource, else the one with `isCurrent`, else the full-size photo or video (`PHAssetExtensions.swift:54-86`). Adjustment data and the iOS 17 photo proxy are excluded (`reference/immich/mobile/ios/Runner/Sync/PHAssetResourceExtensions.swift:9-14`). iCloud download is allowed while hashing only for albums selected for backup (`hash.service.dart:114-117`). The digest is stored on `local_asset_entity.checksum` (`hash.service.dart:140-144`). It is not put on the upload.

The server hashes the `assetData` stream with SHA-1 while writing it (`file-upload.interceptor.ts:118-138`) and stores that digest with `checksumAlgorithm` `sha1` (`reference/immich/server/src/enum.ts:47-51`, `asset-media.service.ts:153-154`). Sidecar bytes are not hashed (`file-upload.interceptor.ts:118`). A client checksum is accepted only as the optional header `x-immich-checksum`, base64 if the string length is 28, otherwise hex (`reference/immich/server/src/utils/request.ts:4-5`, `reference/immich/server/src/enum.ts:25`). This app does not send it. Sync and `GET /api/assets/{id}` return the stored digest as base64 (`reference/immich/server/src/utils/bytes.ts:27-33`). The local skip is string equality between the hasher's base64 and that stored base64.

The upload reader is not the hasher. Backup and manual upload open `photo_manager` `originFile` or `originFileWithSubtype`, and iOS iCloud fallback uses `loadFile` (`storage.repository.dart:15-64`, `105-128`). `photo_manager` is not in this tree, so this note does not claim those calls return the same bytes `getResource` or `setRequireOriginal` hashed. The uploaded filename's extension is taken from the opened file, and a test shows a `.dng` title rewritten to `.jpg` when that is the file opened (`reference/immich/mobile/test/services/background_upload.service_test.dart:146-157`).

An edit on the phone clears the checksum so the new bytes hash again. iOS does that when `adjustmentTime` changes. Android does it when `updatedAt` changes. The old checksum is kept in `previousChecksum` (`local_album.repository.dart:284-296`, `327-358`). That is what `POST /api/stacks` pairs. It is not a second checksum sent to the upload.

## Resumable upload

This app version does not use tus, chunked upload, or an upload-session resource. Each file is one multipart `POST /api/assets`. Foreground resends that whole `POST` once if the socket fails before a response. iOS background sets `retries: 3` on the same single `POST`. No `/api/assets/upload` session route was found in `immich-openapi-specs.json` paths or in the mobile tree. `POST /api/assets/bulk-upload-check` is the server's checksum check (`asset-media.controller.ts:180-193`). This app does not call it, so it is not part of the Contract.

## Glossary

**Agrees, for the upload library.** The same bytes from the same user do not become a second asset. The server insert sets `libraryId` null and stores SHA-1 of the uploaded bytes (`asset-media.service.ts:149-154`). The unique index is `(ownerId, checksum)` where `libraryId` is null (`asset.table.ts:37-43`). A conflict returns the existing id and queues deletion of the file just written (`asset-media.service.ts:197-216`). Lookup is `ownerId` plus checksum plus `libraryId` null (`reference/immich/server/src/repositories/asset.repository.ts:683-693`). Another user's row is not a match. The app's own skip is the same shape: local checksum equals a remote checksum whose `owner_id` is this user (`backup.repository.dart:98-103`). The app never says object storage. The server writes the original with `createWriteStream` under the media location, folder `upload`, then the user id (`reference/immich/server/src/repositories/storage.repository.ts:82-83`, `reference/immich/server/src/enum.ts:362-368`, `reference/immich/server/src/cores/storage.core.ts:108-117`, `356-357`). The app uploads no thumbnail and no sidecar. Metadata extraction is a job the server queues after create (`asset-media.service.ts:187`). The app does not upload those bytes.

**Narrower than "one asset per set of bytes".** The identity is per owner, and only inside the null-library index. An external-library file is a different unique index, and its checksum is SHA-1 of the string `path:` plus the path, not the file bytes (`asset.table.ts:44-48`, `enum.ts:47-51`, `reference/immich/server/src/services/library.service.ts:402-410`). The phone's file hash does not equal that path hash, so the app will still upload, and the server will keep both rows.

**Trash still occupies the checksum.** Neither the candidate join nor `getUploadAssetIdByChecksum` ignores `deletedAt` (`backup.repository.dart:98-103`, `asset.repository.ts:683-693`). A repeat backup of a trashed asset is skipped locally. If the local row is missing and the bytes are uploaded anyway, the server returns the trashed id as `duplicate`. The app treats that as success and does not restore it.

**The app can still send the bytes.** The skip is the local table, which backup success does not update. A second run before sync uploads again. The server then keeps one row. Until that sync, the app does not know it already sent them. The header that would let the server answer before the body is written is unused.

**Live photo and motion photo are two assets.** The app uploads a live photo as a hidden video asset plus a still linked by `livePhotoVideoId` (`foreground_upload.service.dart:336-360`). The candidate checksum is the still's hash only. The server can also pull an embedded motion video out of one uploaded file, SHA-1 that video, and create or reuse a second hidden asset for the same owner (`reference/immich/server/src/services/metadata.service.ts:704-745`, `775-785`). The same owner and a shared `livePhotoCID` are linked the same way (`metadata.service.ts:175-203`). That job is not an app call. It does mean one camera live photo is not one Asset.

**A phone edit is a new upload, then a stack.** Changed `adjustmentTime` (iOS) or `updatedAt` (Android) drops the checksum and keeps the old one as `previousChecksum` (`local_album.repository.dart:284-296`, `351-357`). The new bytes are a new candidate. After the new `POST`, the app stacks the new id in front of the old remote id (`asset.service.dart:201-209`). The old asset remains. In-viewer crop and rotate go through `editAsset` (`asset_api.repository.dart:81-86`), not this upload.

**The stored checksum is not a transcode.** Upload stores the SHA-1 of the `assetData` stream (`file-upload.interceptor.ts:118-138`). This handler does not hash an encoded video. Embedding duplicate detection is a later job: it sets `duplicateId` from nearest embeddings for that owner (`reference/immich/server/src/services/duplicate.service.ts:318-357`, `376-398`). It does not reject the upload and it does not merge the files. The mobile upload path does not call it.
