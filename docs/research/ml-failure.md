# Machine learning when it does not run

What the Immich v3.3.6 server does for face detection, CLIP, OCR, and the person-clustering job that follows a successful detection, when machine learning is disabled or every configured machine-learning URL fails. Read from `reference/immich` at tag `v3.3.6`, commit `587f549f46f1cd1822a06e16dcccecef04ea4565` (`git describe --tags --exact-match HEAD` and `git rev-parse HEAD` both match). This note does not run the server. Clustering's nightly date check compares two strings whose production formats are not both fixed in this tree; that limit is called out below.

The server is the client. `MachineLearningRepository` POSTs multipart `entries` plus `image` or `text` to `{url}/predict`, and pings `{url}/ping`, with no `Authorization` header on either call (`reference/immich/server/src/repositories/machine-learning.repository.ts:130-135`, `162-174`, `228-236`). Face detection, CLIP image and text, and OCR are those calls (`machine-learning.repository.ts:190-225`). Person clustering searches stored face embeddings on the server and does not call the repository (`reference/immich/server/src/services/person.service.ts:570-577`, `reference/immich/server/src/repositories/search.repository.ts:356-378`).

## When machine learning is disabled

"Disabled" is a config flag, not an empty URL list. `machineLearning.urls` is `z.array(z.string()).min(1)`, so a stored config cannot have zero URLs (`reference/immich/server/src/dtos/config.dto.ts:207-210`). The default list is one entry, `IMMICH_MACHINE_LEARNING_URL` or `http://immich-machine-learning:3003`. `machineLearning.enabled` defaults to true unless `IMMICH_MACHINE_LEARNING_ENABLED` is the string `false`. CLIP, facial recognition, and OCR each default to `enabled: true` (`config.dto.ts:619-648`). Saved config is merged over those defaults and then parsed (`reference/immich/server/src/utils/config.ts:81-102`).

A task runs only when the top-level flag and its own flag are both on: smart search is `enabled && clip.enabled`, OCR is `enabled && ocr.enabled`, facial recognition is `enabled && facialRecognition.enabled` (`reference/immich/server/src/utils/misc.ts:96-102`). Duplicate detection also requires smart search (`misc.ts:103-104`). None of these functions read the URL list or the health map.

While `machineLearning.enabled` is false, or availability checks are off, setup does not ping (`machine-learning.repository.ts:107-109`). The per-asset handlers return `JobStatus.Skipped` before `predict`: CLIP (`reference/immich/server/src/services/smart-info.service.ts:89-92`), face detection (`person.service.ts:385-388`), OCR (`reference/immich/server/src/services/ocr.service.ts:33-36`), and clustering (`person.service.ts:544-547`). The queue-all handlers do the same and do not enqueue asset or face jobs (`smart-info.service.ts:69-72`, `person.service.ts:359-362`, `484-493`, `ocr.service.ts:15-18`). Turning the feature back on does not schedule the backlog. CLIP's config handler returns immediately when smart search is off, and when it is on it only adjusts the vector width. A comment says a reindex job should be scheduled and is not (`smart-info.service.ts:34-64`). No `ConfigUpdate` handler queues face detection, OCR, or clustering.

`GET /api/server/features` reports those flags and does not ping (`reference/immich/server/src/app.common.ts:65`, `reference/immich/server/src/controllers/server.controller.ts:99-111`, `reference/immich/open-api/immich-openapi-specs.json:13073-13077`). `getFeatures` sets `smartSearch`, `facialRecognition`, `ocr`, and `duplicateDetection` from the helpers above, plus `importFaces` from `metadata.faces.import` (`reference/immich/server/src/services/server.service.ts:88-110`, `reference/immich/server/src/dtos/server.dto.ts:132-150`). With the flags off, `smartSearch`, `facialRecognition`, and `ocr` are false. With URLs configured but all down, and the flags still on, the same fields stay true. URL health is not a feature flag.

The app's `ServerFeatures` keeps `trash`, `map`, `oauthEnabled`, `passwordLogin`, `ocr`, and `smartSearch`. It does not keep `facialRecognition` (`reference/immich/mobile/lib/models/server_info/server_features.model.dart:9-25`, `reference/immich/mobile/lib/services/server_info.service.dart:41-50`). A search of `mobile/` for `facialRecognition` finds no matches. Context search is the default, and the context menu item is shown, only when the stored flag says `smartSearch` (`reference/immich/mobile/lib/presentation/pages/search/search.page.dart:44-49`, `537-556`). OCR text search is shown only when the stored flag says `ocr` (`search.page.dart:594-611`, `reference/immich/mobile/lib/widgets/common/feature_check.dart:29-36`).

## When every URL fails

`predict` walks the configured URLs, healthy ones first, then the others. A URL that has not been checked is not healthy, so it is still tried (`machine-learning.repository.ts:154-169`). HTTP not-ok and a thrown fetch error are both logged, the URL is marked unhealthy, and the loop continues (`machine-learning.repository.ts:170-185`). Ping failure is the same idea: `fetch` of `{url}/ping` with `AbortSignal.timeout` (default 2000ms) and any throw marks the URL unhealthy (`machine-learning.repository.ts:130-143`, `config.dto.ts:622-626`). An unhealthy URL is not removed. After the last URL fails, `predict` throws `Machine learning request '…' failed for all URLs` (`machine-learning.repository.ts:187`). The `predict` `fetch` itself sets no timeout (`machine-learning.repository.ts:171`). This tree does not say how long a hung socket waits before the runtime rejects it.

The BullMQ worker calls `JobRun` and does not inspect the handler result (`reference/immich/server/src/repositories/job.repository.ts:90-98`, `137-144`). `onJobRun` awaits the handler. `JobStatus.Success` and `JobStatus.Skipped` queue follow-up work. A thrown error is caught, `JobError` is emitted, and the catch does not rethrow (`reference/immich/server/src/services/job.service.ts:85-98`). The worker promise therefore resolves. Default job options are `attempts: 1`, `removeOnComplete: true`, `removeOnFail: false` (`reference/immich/server/src/repositories/config.repository.ts:280-288`). A swallowed throw is a completed job and is deleted. `removeOnFail` does not keep it. There is no second BullMQ attempt. `JobError` logs `Unable to run job handler` and writes an admin notification only for `DatabaseBackup` (`reference/immich/server/src/services/notification.service.ts:81-108`). Telemetry counts the job name as `failed` (`reference/immich/server/src/services/telemetry.service.ts:45-48`). `JobStatus.Failed`, returned when the asset or preview is missing, is not a throw: the job is also completed and removed, and `onDone` does not run (`job.service.ts:91-93`, `enum.ts:988-992`).

Nothing in Postgres records the failure. `asset_job_status` has `facesRecognizedAt`, `metadataExtractedAt`, `duplicatesDetectedAt`, and `ocrAt`. There is no failure column and no CLIP timestamp (`reference/immich/server/src/schema/tables/asset-job-status.table.ts:4-19`). Those timestamps and the `smart_search` row are written only after a successful `predict`. A thrown `predict` leaves them as they were.

## One URL fails and another is healthy

The failed URL is marked unhealthy and the loop tries the next. The first `response.ok` marks that URL healthy and returns its JSON (`machine-learning.repository.ts:165-174`). The handler then follows the success path below. Health only changes order. A URL whose ping failed is still called.

## Face detection

Upload reaches detection only after metadata extraction queues a storage-template job, and that job's success or skip, for `source` `upload` or `copy`, queues thumbnail generation (`reference/immich/server/src/services/storage-template.service.ts:138-149`, `job.service.ts:119-123`). A successful or skipped `AssetGenerateThumbnails` queues `SmartSearch`, `AssetDetectFaces`, and `Ocr` only when `notify` is set or `source` is `upload`. Data that is only `{ id }` queues none of them. The unit test covers both (`job.service.ts:167-182`, `reference/immich/server/src/services/job.service.spec.ts:69-86`). `source` `copy` therefore gets a thumbnail job and does not get these three. The queue does not check the machine-learning flags. A hidden asset is skipped inside the handler and `detectFaces` is not called (`person.service.ts:396-398`). No preview file returns `JobStatus.Failed` before the call (`person.service.ts:390-394`).

On success the handler inserts new `asset_face` rows (default `sourceType` `machine-learning`) and `face_search` embeddings, may delete machine-learning faces that no longer match, and then sets `facesRecognizedAt` (`person.service.ts:406-462`, `reference/immich/server/src/repositories/person.repository.ts:810-834`, `reference/immich/server/src/schema/tables/asset-face.table.ts:50-90`, `reference/immich/server/src/schema/tables/face-search.table.ts:11-16`). New face rows also queue clustering, below. If `predict` throws, none of that runs. No face row, no `face_search` row, `facesRecognizedAt` stays null, and clustering is not queued.

`AssetDetectFacesQueueAll` is not part of the nightly job. It is queued by `PUT /api/jobs/{name}` with command `start` on the face-detection queue (`reference/immich/server/src/controllers/job.controller.ts:45-57`, `reference/immich/server/src/services/queue.service.ts:232-234`). `force: false` selects assets whose `facesRecognizedAt` is null. `force` omitted does not add that filter, so every non-hidden, non-deleted asset with a preview is queued. `force: true` first deletes every machine-learning face, then queues that same full set (`person.service.ts:364-373`, `reference/immich/server/src/repositories/asset-job.repository.ts:180-193`, `450-455`, `reference/immich/server/src/repositories/person.repository.ts:297-298`). The delete does not clear `facesRecognizedAt`. A later non-force run therefore skips assets whose timestamp was already set, even if this forced run deleted their faces and every `predict` then threw. `POST /api/assets/jobs` with `refresh-faces` queues `AssetDetectFaces` for the given ids and does not look at the timestamp (`reference/immich/server/src/controllers/asset.controller.ts:29`, `44-53`, `reference/immich/server/src/enum.ts:647`, `reference/immich/server/src/dtos/asset.dto.ts:66-70`, `reference/immich/server/src/services/asset.service.ts:472-481`).

EXIF face import is not a fallback. It runs only inside metadata extraction when `metadata.faces.import` is true, and that default is false (`reference/immich/server/src/services/metadata.service.ts:401-402`, `902-951`, `config.dto.ts:658-661`, `misc.ts:105`). Those rows are `sourceType` `exif`. Clustering skips them (`person.service.ts:555-557`).

## CLIP

`handleEncodeClip` calls `encodeImage` on the single preview (`smart-info.service.ts:94-103`). Hidden assets are skipped. Any other file count returns `JobStatus.Failed` before the call (`smart-info.service.ts:94-101`). Success upserts `smart_search` (`assetId`, `embedding`) and returns (`smart-info.service.ts:110-118`, `reference/immich/server/src/repositories/search.repository.ts:480-485`, `reference/immich/server/src/schema/tables/smart-search.table.ts:12-18`). A throw writes nothing. There is no CLIP column on `asset_job_status`.

`SmartSearchQueueAll` is only the manual queue start (`queue.service.ts:212-214`). It is not nightly. With `force` omitted or false, the stream is assets that have a preview and no `smart_search` row (`asset-job.repository.ts:212-219`). `force: true` first deletes every `smart_search` row and resets the vector column (`smart-info.service.ts:74-78`, `reference/immich/server/src/repositories/database.repository.ts:322-335`), so a later non-force run does see those assets again. That is the opposite of the face and OCR timestamps, which survive a forced wipe of the result rows.

If the CLIP job returns skipped, and its data `source` is `upload`, `onDone` queues duplicate detection (`job.service.ts:251-255`). A thrown `predict` does not, because `onDone` is not called. Duplicate detection then no-ops unless smart search and `duplicateDetection.enabled` are both on (`reference/immich/server/src/services/duplicate.service.ts:302-307`, `318-323`). A text search calls `encodeText`, which is the same `predict` loop (`search.service.ts:325-339`, `machine-learning.repository.ts:211-214`).

## OCR

`handleOcr` calls `ocr` on the preview path (`ocr.service.ts:38-47`). Hidden is skipped. No preview returns `JobStatus.Failed` (`ocr.service.ts:38-45`). Success replaces that asset's `asset_ocr` rows and `ocr_search` text, then sets `ocrAt` (`ocr.service.ts:47-51`, `reference/immich/server/src/repositories/ocr.repository.ts:59-74`). A throw does none of this. An empty recognition still counts as success: it deletes any previous OCR rows and search text and sets `ocrAt` (`ocr.repository.ts:70-74`).

`OcrQueueAll` is only the manual queue start (`queue.service.ts:248-249`). With `force` omitted or false, the stream is non-hidden, non-deleted assets whose `ocrAt` is null (`asset-job.repository.ts:459-470`). `force: true` truncates `asset_ocr` and `ocr_search` first (`ocr.service.ts:20-22`, `ocr.repository.ts:30-34`) and does not clear `ocrAt`. A later non-force run skips assets that already had `ocrAt` set.

## Person clustering after a successful detection

Clustering does not call the machine-learning service. It reads `maxDistance` and `minFaces` from config and runs `searchFaces` against `face_search` (`person.service.ts:570-577`, `search.repository.ts:356-378`). URLs being down does not change that, as long as `isFacialRecognitionEnabled` is still true. If the flag is off, the job returns `Skipped` and leaves `personGroupId` null (`person.service.ts:544-547`, `565-567`).

Detection queues clustering only when it inserted at least one new face: one `FacialRecognition` job per new face, plus `FacialRecognitionQueueAll` with `force: false` (`person.service.ts:454-460`). Updating an embedding on a face that already matched does not queue it. A thrown `predict` does not reach this. The per-face job is the attempt. The queue-all job, if it sees other facial-recognition jobs already waiting and `force` is not true, returns `Skipped` without queueing and without writing `lastRun` (`person.service.ts:509-519`). The facial-recognition queue is not given the configured concurrency; it stays at one (`queue.service.ts:258-264`). `FacialRecognitionQueueAll` is deduplicated by job name (`job.repository.ts:271-273`).

The per-face job assigns a person, or creates one when the face is a core face and no neighbor already has a person (`person.service.ts:586-632`). A core face has at least `minFaces` neighbors, including itself, and the asset is on the timeline. The default `minFaces` is 3 (`config.dto.ts:635-640`). A non-core face that is not yet deferred is queued again with `deferred: true`, and this run returns `Skipped` (`person.service.ts:590-593`). A face that only matches itself, when `minFaces` is greater than 1, returns `Skipped` and is not assigned (`person.service.ts:579-583`). A deferred non-core face with no existing person returns `Success` without writing `personGroupId` (`person.service.ts:610-633`). None of these outcomes record a failure. The face row and its embedding stay.

Nightly jobs, default `00:00`, include `FacialRecognitionQueueAll` with `force: false` and `nightly: true` when `nightlyTasks.clusterNewFaces` is true, which it is by default (`queue.service.ts:34-36`, `267-299`, `config.dto.ts:721-727`). They do not include face-detection, CLIP, or OCR queue-all. The nightly run skips when `facial-recognition-state.lastRun` and the latest `facesRecognizedAt` are both set and `lastRun > latestFaceDate` (`person.service.ts:497-506`, `reference/immich/server/src/types.ts:555`, `reference/immich/server/src/enum.ts:376`). `lastRun` is `new Date().toISOString()` (`person.service.ts:524-537`). `latestFaceDate` is `max(asset_job_status.facesRecognizedAt)::text` (`person.repository.ts:932-939`). The comparison is JavaScript string order. The unit test stubs ISO strings on both sides (`reference/immich/server/src/services/person.service.spec.ts:1011-1053`). This repository does not fix how Postgres renders that `::text`, so this note does not say whether a detection from the same calendar day sorts after `lastRun`. A clustering job that skips or throws does not change `facesRecognizedAt` or `lastRun`. If the guard already skips, that failure does not cause the next night to run. When the guard does not skip, the run queues visible, non-deleted machine-learning faces whose `personGroupId` is null, then sets `lastRun` (`person.service.ts:526-537`, `person.repository.ts:305-321`). A manual start without `nightly` does not apply the date guard (`queue.service.ts:236-238`). `regeneratePeople` queues the same job with `force: true`, which unassigns machine-learning faces before requeueing (`reference/immich/server/src/services/cluster-group.service.ts:75-81`, `person.service.ts:511-514`).

## What the asset looks like until the work succeeds

The asset row is unchanged. Sync does not read `asset_job_status`, `smart_search`, or a failure flag. A search of `sync.repository.ts` for `job_status`, `facesRecognized`, `ocrAt`, and `smartSearch` finds no matches. `PeopleV1`, `AssetFaceV3`, and `AssetOcrV1` stream existing `person`, `asset_face`, and `asset_ocr` rows (`reference/immich/server/src/services/sync.service.ts:915-926`, `950-961`, `1007-1030`, `reference/immich/server/src/repositories/sync.repository.ts:438-454`, `503-512`, `855-860`). No row means nothing new is emitted for that asset. The app already reads those streams as the people list, the faces on an asset, and the OCR overlay (`docs/research/ml-results.md:9-21`, `37`). Face boxes are stored and not drawn. OCR boxes are drawn only when rows exist (`docs/research/ml-results.md:21`, `37`). Until clustering assigns a `personGroupId`, a face row would still not appear on those screens, because both queries join through `person_id` (`docs/research/ml-results.md:21`). With no face and no person, the people card and the asset's people section stay empty. The people UI is not hidden by `facialRecognition`, because the app does not store that flag.

Smart search is `POST /api/search/smart`. The query inner-joins `smart_search`, so an asset with no embedding is not a hit (`reference/immich/server/src/services/search.service.ts:168-197`, `search.repository.ts:320-336`). With the flag off the route throws `Smart search is not enabled` before any URL call (`search.service.ts:177-180`). With the flag on, a text query calls `encodeText`. If every URL fails, that throw becomes HTTP 500 `{ message: 'Internal server error' }` (`reference/immich/server/src/middleware/global-exception.filter.ts:65-70`). "View similar photos" sends `queryAssetId` and does not check `smartSearch` (`docs/research/ml-results.md:31`). The server then loads the stored embedding and throws HTTP 400 `Asset {id} has no embedding` when the row is missing (`search.service.ts:343-350`). That throw is a `BadRequestException`, and it is reached only after the smart-search flag check above. The app turns a thrown search into a null result (`docs/research/ml-results.md:33`).

OCR text search is `POST /api/search/metadata`. It does not check the OCR flag. A non-empty `ocr` inner-joins `ocr_search` (`reference/immich/server/src/services/search.service.ts:74-113`, `reference/immich/server/src/utils/database.ts:517-520`). No row means the asset is not a hit. The route itself still returns 200. Filename and description search do not need that row.

While the flags are on but the URLs are down, the app still offers context search and OCR text search, because `GET /api/server/features` is unchanged. Context search fails on the text embedding call. OCR text search succeeds and does not return this asset. While the flags are off, context search and OCR text search are hidden, and a smart-search call that is made anyway is HTTP 400 `Smart search is not enabled` (`search.service.ts:177-180`).

## Retries

BullMQ does not retry the failed `predict`. `attempts` is 1, and the thrown error is not allowed to fail the Bull job (`config.repository.ts:284-288`, `job.service.ts:94-96`). The incomplete asset is the retry state: `facesRecognizedAt` null, `ocrAt` null, no `smart_search` row, and, after a detection that did succeed, a machine-learning face with `personGroupId` null.

What queues the work again:

- Thumbnail generation that finishes as success or skipped, and whose data has `notify` or `source: 'upload'` (`job.service.ts:167-182`, `job.service.spec.ts:69-86`). The upload chain does that: metadata extraction passes `source` through the storage-template job into thumbnail generation (`storage-template.service.ts:138-141`, `job.service.ts:119-123`). Showing an asset that had been hidden sets `notify: true` (`notification.service.ts:146-148`). `POST /api/assets/jobs` `regenerate-thumbnail` and the nightly missing-thumbnail stream pass only `{ id }`, so those thumbnail jobs do not queue CLIP, faces, or OCR (`asset.service.ts:489-491`, `reference/immich/server/src/services/media.service.ts:79`). Nightly `missingThumbnails` also only selects assets missing a thumbnail, a preview, a thumbhash, or an edited full-size file (`queue.service.ts:291-293`, `asset-job.repository.ts:64-102`). An asset that already has those files and failed CLIP, faces, or OCR is not in that stream.
- `PUT /api/jobs/{name}` command `start` for `smartSearch`, `faceDetection`, `ocr`, or `facialRecognition` (`job.controller.ts:45-57`, `queue.service.ts:212-249`). Non-force CLIP and OCR select the missing rows and null `ocrAt`. Non-force face detection selects null `facesRecognizedAt` only when `force` is exactly false. Omitted `force` requeues every preview asset.
- `POST /api/assets/jobs` `refresh-faces`, which is face detection only (`asset.service.ts:477-481`). There is no per-asset CLIP or OCR name on that enum (`asset.dto.ts:66-70`).
- Nightly clustering of faces that already exist, under the `lastRun` guard above. It does not re-run detection.

A search of the server job names finds no other queue site for `SmartSearchQueueAll`, `AssetDetectFacesQueueAll`, or `OcrQueueAll`. Re-enabling the flags does not add one.
