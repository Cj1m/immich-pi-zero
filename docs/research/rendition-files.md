# Rendition files

Where the v3.3.6 server stores the thumbnail and preview files that `GET /api/assets/{id}/thumbnail` reads, and the encoded video that `GET /api/assets/{id}/video/playback` prefers over the Original. Read from `reference/immich` at tag `v3.3.6`, commit `587f549f46f1cd1822a06e16dcccecef04ea4565` (`git describe --tags --exact-match HEAD` and `git rev-parse HEAD` both match). This note does not run the server.

## Rows

Thumbnail, preview, and the encoded video are rows in `asset_file`, not columns on `asset`. The path column is `path`. The type column stores the `AssetFileType` string: `thumbnail`, `preview`, or `encoded_video`. The same enum also has `fullsize` and `sidecar` (`reference/immich/server/src/enum.ts:54-63`, `reference/immich/server/src/schema/tables/asset-file.table.ts:16-36`).

A row is not one per asset. The unique key is `(assetId, type, isEdited)` (`asset-file.table.ts:17`). An edited copy is the same type with `isEdited` true, not a different type string. `isEdited` defaults to false (`asset-file.table.ts:41-42`). Thumbnail and preview therefore have up to two rows each. The encoded video is written only with `isEdited` false, so playback has one row to find.

`viewThumbnail` casts `size` to that type string. Omitted `size` is `thumbnail`. `thumbnail`, `preview`, and `fullsize` are the same strings as the file types (`reference/immich/server/src/dtos/asset-media.dto.ts:8-17`, `reference/immich/server/src/services/asset-media.service.ts:266-271`). `getForThumbnail` left-joins `asset_file` on asset id and type, does not filter `isEdited`, orders `isEdited` descending when `edited` is true and ascending when it is false, and takes the first row (`reference/immich/server/src/repositories/asset.repository.ts:1173-1182`). Both rows present: `edited=true` opens the edited file, `edited=false` opens the other. Only one row present: that path is opened either way. No row: `path` is null.

Omitted `edited` is false (`asset-media.dto.ts:28`, `asset-media.service.ts:270`). The thumbnail URL builder defaults `edited` to true. Playback's URL has no `edited` query (`reference/immich/mobile/lib/utils/image_url_builder.dart:9-20`). A shared-link session forces `edited` true before the thumbnail lookup (`asset-media.service.ts:262-264`). `viewThumbnail` is awaited before `sendFile` (`asset-media.controller.ts:137-140`). A null path is `NotFoundException` from that call, which the global filter returns as 404. A missing asset row makes `executeTakeFirstOrThrow` throw, and that error is not an `HttpException`, so the filter returns 500 (`reference/immich/server/src/middleware/global-exception.filter.ts:41-44`, `65-69`).

For `size=thumbnail` and `size=preview`, a null path throws `NotFoundException`. There is no fall-through to the Original and no redirect (`asset-media.service.ts:284-286`). The controller `sendFile`s the `ImmichFileResponse` (`reference/immich/server/src/controllers/asset-media.controller.ts:137-140`).

`playbackVideo` loads a video asset and uses `encodedVideoPath || originalPath` (`asset-media.service.ts:300-315`). `getForVideo` restricts `asset.type` to `VIDEO` and selects the `encoded_video` path with `withFilePath`, whose `isEdited` argument defaults to false (`asset.repository.ts:1186-1193`, `reference/immich/server/src/utils/database.ts:235-242`). A missing encoded row is SQL null, so the opened file is `asset.originalPath`, the Original. That is not a 404. A missing asset, or an asset that is not a video, throws `NotFoundException` before that choice (`asset-media.service.ts:305-307`). The controller `sendFile`s whichever path was chosen (`asset-media.controller.ts:171-177`). `sendFile` checks that the path is readable and, if it is not, responds 404. It does not try the other file (`reference/immich/server/src/utils/file.ts:57-78`). An encoded row whose file is gone is therefore 404, not a fallback to the Original.

`size=fullsize` is the same `AssetGenerateThumbnails` job, in the same `thumbs` directory, named `{id}_fullsize.{format}` or `{id}_fullsize_edited.{format}`. `useEdits` forces that branch. `image.extractEmbedded` defaults to false, so an edited still is converted with sharp and the file is marked edited. A non-web Original is also written when `image.fullsize.enabled` is on or the projection is `EQUIRECTANGULAR`. The default `image.fullsize.enabled` is false and the default format is `jpeg` (`reference/immich/server/src/services/media.service.ts:256-264`, `329-367`, `reference/immich/server/src/dtos/config.dto.ts:709-714`). A video or a `.gif` does not get one. The viewer does not request `size=fullsize`. A client that does, and finds no row, is redirected to `size=preview`. A web-supported Original with `edited` false is redirected to the original endpoint even when a fullsize file exists (`asset-media.service.ts:273-281`, `asset-media.controller.ts:141-159`).

## Directories

The root is the media location. `IMMICH_MEDIA_LOCATION`, when set, must be an absolute path (`reference/immich/server/src/dtos/env.dto.ts:15`, `52`, `reference/immich/server/src/repositories/config.repository.ts:356-358`). Unset, `detectMediaLocation` uses `/data` or `/usr/src/app/upload` when exactly one of those directories exists, and otherwise `/usr/src/app/upload` (`reference/immich/server/src/services/storage.service.ts:23-44`). Bootstrap stores that choice on `StorageCore` and in system metadata under `MediaLocation` (`storage.service.ts:46-48`, `99-133`, `reference/immich/server/src/enum.ts:373-374`). There is no second join at request time.

`StorageFolder` values used here are `thumbs`, `encoded-video`, and, for the Original, `upload` and `library` (`enum.ts:362-369`). `getBaseFolder` is `join(mediaLocation, folder)`. `getNestedFolder` adds the owner id and then `filename.slice(0, 2)` and `filename.slice(2, 4)`. `getNestedPath` joins the filename itself (`reference/immich/server/src/cores/storage.core.ts:108-118`, `356-362`).

Thumbnail and preview have no separate subdirectory. `getImagePath` uses folder `thumbs` and filename `{assetId}_{fileType}{isEdited ? '_edited' : ''}.{format}` (`storage.core.ts:124-129`). `fileType` is the enum string, so the names are `{id}_thumbnail.webp` and `{id}_preview.jpeg` at the defaults. `image.thumbnail.format` defaults to `webp`, `image.preview.format` to `jpeg` (`config.dto.ts:695-707`, `enum.ts:600-603`). The first four characters of that filename are the first four characters of the asset id, so the absolute path is `{mediaLocation}/thumbs/{ownerId}/{id[0:2]}/{id[2:4]}/{id}_thumbnail.webp`, and the same pattern for preview and fullsize. An edited file inserts `_edited` before the extension.

`getEncodedVideoPath` uses folder `encoded-video` and filename `{assetId}.mp4` (`storage.core.ts:132-134`). The absolute path is `{mediaLocation}/encoded-video/{ownerId}/{id[0:2]}/{id[2:4]}/{id}.mp4`. The extension is fixed. It is not a config format.

Those `asset_file.path` values are absolute. `getImageFile` stores `getImagePath` as returned, and `handleVideoConversion` stores `getEncodedVideoPath` as returned (`media.service.ts:864-872`, `561`, `630-635`). `sendFile` passes that string to `res.sendFile` (`file.ts:54-73`). It does not prefix the media location again. An older migration rewrote relative `upload/...` paths to `/usr/src/app/upload/...` when `IMMICH_MEDIA_LOCATION` was unset (`reference/immich/server/src/schema/migrations/1752759108283-ConvertToAbsolutePaths.ts:6-26`). Current writers do not store a relative path.

The Original that playback falls back to is `asset.originalPath` on `asset`, not an `asset_file` row (`reference/immich/server/src/schema/tables/asset.table.ts:24`, `80-81`). Upload writes it under `upload`, `{mediaLocation}/upload/{userId}/{uuid[0:2]}/{uuid[2:4]}/{uuid}{extension}`, where `uuid` is the upload id (`reference/immich/server/src/middleware/file-upload.interceptor.ts:112-115`, `reference/immich/server/src/services/asset-media.service.ts:91-107`). `storageTemplate.enabled` defaults to false. When it is on, `StorageTemplateMigrationSingle` may move that Original under `library` (`config.dto.ts:690-693`, `storage.core.ts:112-114`, `reference/immich/server/src/services/storage-template.service.ts:282`, `344-345`). The move renames the Original and, if present, the sidecar. It does not rename thumbnail, preview, or `encoded_video` files. It returns without moving when the Original is external or already under `encoded-video` (`storage-template.service.ts:227-231`, `244-260`).

The same `thumbs` folder holds person thumbnails at `{mediaLocation}/thumbs/{ownerId}/{personGroupId[0:2]}/{personGroupId[2:4]}/{personGroupId}.jpeg` (`storage.core.ts:120-121`). That file is `GET /api/people/{id}/thumbnail`, not this route. The same `encoded-video` folder also holds Android motion Originals, `{motionId}-MP.mp4`, which are `originalPath` and not an `encoded_video` row (`storage.core.ts:144-146`, `reference/immich/server/src/services/metadata.service.ts:745`), and HLS session directories (`storage.core.ts:136-137`). Playback does not open those.

## Jobs

One job writes the thumbnail and the preview. The name is `AssetGenerateThumbnails` (`enum.ts:891`). The handler is `MediaService.handleGenerateThumbnails` (`media.service.ts:191-231`).

After upload, `uploadAsset` queues `AssetExtractMetadata` with `source: 'upload'` (`asset-media.service.ts:187`). `handleMetadataExtraction` does not return a job status; it emits `AssetMetadataExtracted` with that source (`metadata.service.ts:411-417`). `onAssetMetadataExtracted` queues `StorageTemplateMigrationSingle` with the same source (`storage-template.service.ts:138-141`). That handler returns `Skipped` when the storage template is disabled, which is the default, and `Success` after a move (`storage-template.service.ts:143-149`, `172`). `JobRepository.run` returns the handler's status, and `onDone` runs for `success` and `skipped` (`reference/immich/server/src/repositories/job.repository.ts:137-145`, `reference/immich/server/src/services/job.service.ts:89-93`). For source `upload` or `copy` it queues `AssetGenerateThumbnails` with the same data (`job.service.ts:119-122`). A hidden asset makes the thumbnail handler return `Skipped` before it writes (`media.service.ts:201-204`). `onDone` still runs. It reloads the asset without a visibility filter, and for a video with source `upload` it still queues `AssetEncodeVideo` (`job.service.ts:167-186`, `reference/immich/server/src/repositories/asset.repository.ts:519-527`).

A still whose name does not end in `.gif` is `generateImageThumbnails`. That decodes with sharp and writes both files with `MediaRepository.generateThumbnail`, which calls sharp `toFile` on the final path (`media.service.ts:291-327`, `reference/immich/server/src/repositories/media.repository.ts:181-190`). A video, or a file whose `originalFileName` ends in `.gif`, is `generateVideoThumbnails`. That calls `mediaRepository.transcode` twice, once per path. `ThumbnailConfig` replaces the usual codec options with one frame (`-frames:v 1`, `-update 1`) and no `-c:v`. The path still ends in the configured format (`media.service.ts:207-209`, `493-521`, `reference/immich/server/src/utils/media.ts:145-152`, `519-521`, `media.repository.ts:397-404`, `440-444`). Those calls pass the final path. They do not build a temporary rendition and rename it. `StorageCore.moveFile` renames an existing file during `AssetFileMigration` and during a storage-template move of the Original (`storage.core.ts:241-244`, `325-337`, `media.service.ts:138-149`). It is not how these bytes are first written.

`syncFiles` then upserts. The conflict key is `(assetId, type, isEdited)`, and the update sets `path`, `isProgressive`, and `isTransparent` (`media.service.ts:776-810`, `asset.repository.ts:1033-1053`). A previous row of the same type and `isEdited` whose path changed is queued as `FileDelete`, which unlinks it (`media.service.ts:800-822`, `reference/immich/server/src/services/storage.service.ts:137-148`). The same path is overwritten in place and the old file is not deleted. A previous thumbnail, preview, or fullsize row that this run did not regenerate is deleted from `asset_file` and queued for the same unlink. Nightly `missingThumbnails`, default true, queues `AssetGenerateThumbnailsQueueAll` with `force: false` (`config.dto.ts:721-727`, `reference/immich/server/src/services/queue.service.ts:291-293`). With `force` false that queue's stream is a non-hidden asset that has no thumbnail row, no preview row, a null thumbhash, an edit without an edited fullsize row, or, when fullsize generation is enabled, a web-unsupported name without a fullsize row (`reference/immich/server/src/repositories/asset-job.repository.ts:64-100`). The queue handler then queues `AssetGenerateThumbnails` only when `force` is set or the asset is not edited, and queues `AssetEditThumbnailGeneration` when the asset is edited (`media.service.ts:68-87`).

Edited thumbnail and preview use types `thumbnail` and `preview` with `isEdited` true, plus `fullsize` when the edited still takes the fullsize branch. The filename gains `_edited`. `handleGenerateThumbnails` calls `generateEditedThumbnails`, which calls `generateImageThumbnails` with `useEdits` true only for an image that has edits (`media.service.ts:218-221`, `826-831`). Saving or clearing edits queues a second job, `AssetEditThumbnailGeneration` (`enum.ts:883`). `editAsset` and `removeAssetEdits` both queue it (`reference/immich/server/src/services/asset.service.ts:609-610`, `627-628`). `handleAssetEditThumbnailGeneration` writes only the edited set, or, when no edits remain, syncs that set to empty and deletes the edited rows (`media.service.ts:154-168`, `776-818`). `editAsset` rejects anything that is not an image (`asset.service.ts:562-564`). Playback does not open an edited video. `withFilePath` keeps `isEdited` false, and `handleVideoConversion` upserts `isEdited: false` (`media.service.ts:630-635`).

The encoded file's job is `AssetEncodeVideo` (`enum.ts:885`). The handler is `handleVideoConversion` (`media.service.ts:553-637`). On the upload chain it is queued from `onDone` of `AssetGenerateThumbnails` when the asset type is `VIDEO` and `source` is `upload` or `notify` is set (`job.service.ts:167-186`). Extracting an embedded motion video also queues it for the new motion asset, after writing that Original to the `-MP.mp4` path, and only when that path was not already on disk (`metadata.service.ts:801-808`). `onDone` does not queue the job for an image.

The handler reads `ffmpeg.transcode`. The default is `required` (`config.dto.ts:572`, `enum.ts:498-504`). It skips, and returns `skipped`, when `getTranscodeTarget` is `none` and `isRemuxRequired` is false (`media.service.ts:575-587`). Under `required`, video must be transcoded when the codec is outside `acceptedVideoCodecs` or `pixelFormat` does not end in `420p`. The default accepted video codec is `h264`. Audio must be transcoded when a stream exists and its codec is outside `acceptedAudioCodecs`. The default list is `aac`, `mp3`, and `opus`. `disabled` skips both. `all` transcodes both. `optimal` also transcodes when the smaller edge is above `targetResolution` (default `720`). `bitrate` also transcodes when the stream bitrate is above `maxBitrate` (default `0`, which disables that check) (`media.service.ts:640-730`, `config.dto.ts:554-572`). Remux still runs when the policy is not `disabled` and the container is neither `mp4` nor in `acceptedContainers` (default `mov`, `ogg`, `webm`) (`media.service.ts:718-730`, `enum.ts:538-543`). A skip that finds an existing `encoded_video` row queues `FileDelete` for that path and deletes the row (`media.service.ts:577-582`). No video metadata, or no width and height, returns `failed` and writes nothing (`media.service.ts:564-572`). `getForVideoConversion` inner-joins `asset_exif` and `asset_video`, so a video without those rows is `failed` as well (`asset-job.repository.ts:349-362`).

On success, ffmpeg's `.output` is the final `{id}.mp4` path (`media.repository.ts:440-444`). `ffmpeg.twoPass` defaults to false. When it is on, pass 1 writes `/dev/null` and pass 2 writes that same final path (`config.dto.ts:570`, `media.repository.ts:411-428`). The handler then upserts `asset_file` (`assetId`, type `encoded_video`, `isEdited` false, that path). Conflict updates `path` only (`media.service.ts:630-635`, `asset.repository.ts:1016-1030`). It does not queue a delete of a previous encoded file. The path does not change for a given asset, so a second run overwrites the same file.

Thumbhash is not an `asset_file`. It is `asset.thumbhash`, nullable `bytea` (`asset.table.ts:113-114`). `handleGenerateThumbnails` sets it from the edited preview when edits were generated, otherwise from the preview it just wrote (`media.service.ts:223-228`). `generateThumbhash` resizes with sharp and calls the `thumbhash` package (`media.repository.ts:242-252`). `viewThumbnail` does not read the column.
