# Album activity

Which HTTP calls the v3.3.6 mobile app makes for the comments screen, and what a missing field does to that screen and to the comments-and-likes switch. Read from `reference/immich` at tag `v3.3.6`, commit `587f549f46f1cd1822a06e16dcccecef04ea4565` (`git describe --tags --exact-match HEAD` and `git rev-parse HEAD` both match). This note does not run the server or the app.

An Activity is a like or a comment. The app's word for the screen is comments. The switch is labeled comments and likes.

`mobile/generated/openapi` is not in the checkout. Paths below are the OpenAPI paths, prefixed with `/api` because the client `basePath` is a URL that ends in `/api` (`reference/immich/mobile/lib/services/api.service.dart:16`, `56-57`, `115-119`, `reference/immich/open-api/immich-openapi-specs.json:18391-18394`). Nest mounts `activities` under that prefix (`reference/immich/server/src/app.common.ts:65`, `reference/immich/server/src/controllers/activity.controller.ts:19`). A checked-in generated DTO reads a required field with `mapValueOfType<T>(json, name)!`, and a required enum with `fromJson(...)!` (`reference/immich/open-api/patch/asset_edit_action_item_response_dto.dart.patch:12-13`). The generator template's required-key asserts are debug-only and are patched out (`reference/immich/open-api/templates/mobile/serialization/native/native_class.mustache.patch`). A missing required value throws. `checkNull` throws `NoResponseDtoError` when the body is null (`reference/immich/mobile/lib/repositories/api.repository.dart:4-9`, `reference/immich/mobile/lib/data/server/errors.dart:6-10`).

The switch's `PATCH /api/albums/{id}` is already in [Albums, trash, and shared links](albums-trash-and-shared-links.md). This note says what a missing field does to that switch. It does not re-inventory rename, order, or cover.

## How the screen opens

The album page shows the comments button when the local album's `isActivityEnabled` is true and `isShared` is true (`reference/immich/mobile/lib/widgets/common/remote_album_sliver_app_bar.dart:85-88`). The tap pushes `ActivitiesRoute` with the album and no asset (`reference/immich/mobile/lib/presentation/pages/remote_album.page.dart:184-185`).

On that album read, `isShared` is `count(distinct album user id) > 0` after a join that keeps only the owner row (`reference/immich/mobile/lib/infrastructure/repositories/remote_album.repository.dart:44-52`, `73-81`, `104-112`, `122-131`). Every album the query returns has that count above zero, so `isShared` is true. The button is gated by `isActivityEnabled`. An album with no owner row is absent from the query, so it has no button. The HTTP mapper's `albumUsers.length > 2` is a different flag, used when a create or update response is turned into a `RemoteAlbum` (`reference/immich/mobile/lib/repositories/album_api_repository.dart:141`). The button does not read it.

The viewer shows the same button under the same two flags, and passes the current asset id and name when that asset is remote (`reference/immich/mobile/lib/presentation/widgets/asset_viewer/viewer_top_app_bar.widget.dart:40-60`). While those flags hold, the viewer also watches the asset's activity list, which is the list call below (`viewer_top_app_bar.widget.dart:40-41`).

A link whose host is `activity` reads `albumId`. A missing local album, or `isActivityEnabled == false`, opens nothing. Otherwise it opens `ActivitiesRoute` with the album and no asset (`reference/immich/mobile/lib/services/deep_link.service.dart:49-55`, `135-142`). It does not check `isShared`.

The options switch is a separate page. Only the owner sees it (`reference/immich/mobile/lib/presentation/pages/album_options.page.dart:34`, `219-236`). It displays `album.isActivityEnabled` from the route.

## What is not a call

Activity is not in the sync type list (`reference/immich/mobile/lib/infrastructure/repositories/sync_api.repository.dart:45-72`) and not in the sync parse map (`sync_api.repository.dart:145-208`). Rows live in the in-memory activity store. The store says it reacts to in-memory edits, not to later HTTP changes (`reference/immich/mobile/lib/data/store/activity.dart:13-23`).

`GET /api/activities/statistics` exists (`activity.controller.ts:54-62`, `immich-openapi-specs.json:165-168`). A search of `mobile/lib` finds no `getActivityStatistics` call. The comments screen does not ask for the counts.

The server's list and create do not read `isActivityEnabled` (`reference/immich/server/src/services/activity.service.ts:20-68`). The flag is only the app's gate.

## Calls

### `GET /api/activities`

- When: the comments screen watches `Store.activity.list(album.id, assetId: assetId)` (`reference/immich/mobile/lib/presentation/pages/activities.page.dart:26`). The album page passes no asset. The viewer page passes the asset id. The first watch fetches. A later watch of the same pair uses the memory cache (`reference/immich/mobile/lib/data/store/activity.dart:20-23`, `28-36`).
- Method and path: `GET /api/activities`. Operation `getActivities` (`immich-openapi-specs.json:4-7`). Query `albumId` is required. `assetId`, `level`, `type`, and `userId` are optional (`immich-openapi-specs.json:8-57`). The app sends `albumId`, and `assetId` only when the caller passed one (`reference/immich/mobile/lib/data/server/activity.dart:17-18`). It does not send `level`, `type`, or `userId`.
- What comes back: without `assetId` and without `level`, the server does not filter on asset, so the album page gets album-level rows and asset rows (`activity.service.ts:22-27`, `reference/immich/server/src/repositories/activity.repository.ts:39-44`). With `assetId`, only that asset's rows. `type` is not sent, so likes and comments both return. Oldest `createdAt` is first (`activity.repository.ts:45`, `activity.controller.ts:27-28`). A left join drops a row whose asset exists and has `deletedAt` set. A row with no asset, including an album-level row, stays, because `asset.deletedAt IS NULL` is true when the join misses (`activity.repository.ts:38`, `44`).
- Response fields the app requires: `checkNull` throws on a null body. Each item is `ActivityResponseDto`. Required keys are `assetId`, `createdAt`, `id`, `type`, and `user` (`immich-openapi-specs.json:18445-18485`). `assetId` is nullable. `comment` is not required. `user` is `UserResponseDto`, whose required keys are `avatarColor`, `email`, `id`, `name`, `profileChangedAt`, and `profileImagePath` (`immich-openapi-specs.json:33556-33594`). `type` is `comment` or `like` (`immich-openapi-specs.json:27052-27058`). There is no `albumId` on the DTO. The app stamps the requested `albumId` onto every row (`activity.dart:38-46`).
- The mapper reads `id`, `createdAt`, `type`, `user`, `assetId`, and `comment` (`activity.dart:38-46`). `comment` uses `orElse(null)`, so a missing comment is null. `type` of `comment` is a comment and `type` of `like` is a like. A missing `type` throws before the mapper, because `type` is required. The screen then reads `user.id`, `user.name`, `createdAt`, `type`, `comment`, and `assetId` (`reference/immich/mobile/lib/widgets/activities/comment_bubble.dart:29-32`, `109-118`, `145-146`).
- A throw from `getAll`, including a missing required key, is caught. The watch gets an empty list (`activity.dart` store: `30-36`). It does not become the error body. `widgetWhen` draws the error scaffold only when the value has an error and no data (`reference/immich/mobile/lib/extensions/asyncvalue_extensions.dart:29-34`). An empty list takes the data branch: no rows, and the text field still sits at the bottom (`activities.page.dart:61-90`). The field's enabled flag is the route album's `isActivityEnabled`, not the list.
- Server status on success is 200 (`immich-openapi-specs.json:59-70`). Permission on the controller is `activity.read` (`activity.controller.ts:24`).

### `POST /api/activities`

- When: send on the text field creates a comment. The like button creates a like, or deletes one. Both can name an asset.
- Comment: the field ignores a blank trim, then calls `onSubmit` and clears the text before that future finishes (`reference/immich/mobile/lib/presentation/widgets/album/activity_text_field.dart:62-70`). The page calls `addComment(album.id, comment, assetId: assetId)` with the route's asset id (`activities.page.dart:37-44`). The route asset is null on the album page and on the activity deep link. It is the viewer's asset when the viewer opened the screen.
- Like: the button in the comments app bar is `LikeActivityActionButton` (`activities.page.dart:58`). It does not read the route's `assetId`. It reads the viewer's current asset (`reference/immich/mobile/lib/presentation/widgets/action_buttons/like_activity_action_button.widget.dart:21-25`, `33-36`). The album comes from `currentRemoteAlbumProvider`, which the page overrides to the route album (`activities.page.dart:47-48`, `reference/immich/mobile/lib/providers/infrastructure/current_album.provider.dart:5-18`). A filled thumb is a like whose user is the signed-in user and whose `assetId` equals that viewer asset (`like_activity_action_button.widget.dart:45-47`). A tap on an existing like deletes it. A tap with none creates one. The same button is the viewer's like action, under the same album flags (`reference/immich/mobile/lib/utils/action_button.utils.dart:140-144`).
- Method and path: `POST /api/activities`. No query. Operation `createActivity` (`immich-openapi-specs.json:106-108`). Body is `ActivityCreateDto`.
- Request: `albumId` and `type` are required. `assetId` and `comment` are optional (`immich-openapi-specs.json:18416-18443`). `type` is `comment` or `like`. The app sends `albumId`, `type`, `assetId` only when it has one, and `comment` only when it has one (`activity.dart:22-28`). A like omits `comment`. The server rejects a comment whose text is missing or blank, and rejects a comment on a like (`reference/immich/server/src/dtos/activity.dto.ts:50-62`). The field never submits a blank trim.
- A second like by the same user for the same album, and the same asset or the album itself, does not insert. The server returns the existing row and sets status 200 (`activity.service.ts:49-68`, `activity.controller.ts:47-51`). A comment always inserts. The documented success status is 201 (`immich-openapi-specs.json:121-130`). The generated client is not in the checkout, so this note does not say whether a 200 body is accepted. The app requires a non-null `ActivityResponseDto` (`activity.dart:29-30`). The fields are the list item's fields.
- The new row is cached only after that parse (`activity.dart` store: `51-57`, `65-69`). A throw skips the cache. The page and the like button catch it and show nothing (`activities.page.dart:37-42`, `like_activity_action_button.widget.dart:32-40`). The comment text is already cleared. The list stays as it was. Server permission is `activity.create` (`activity.controller.ts:36`).

### `DELETE /api/activities/{id}`

- When: the signed-in user owns the row, or owns the album (`comment_bubble.dart:29-30`). Anyone else gets no swipe. A swipe asks for confirmation. Cancel sends nothing. Confirm calls `remove` (`comment_bubble.dart:51-57`, `126-128`, `reference/immich/mobile/lib/widgets/activities/dismissible_activity.dart:14-33`). The like button deletes the same way when the thumb is already filled.
- Method and path: `DELETE /api/activities/{id}`. No query and no body. Operation `deleteActivity` (`immich-openapi-specs.json:238-241`). `id` is the activity id, a uuid. Success status is 204 (`activity.controller.ts:65-74`, `immich-openapi-specs.json:255-257`).
- The app passes the id through `checkNull` (`activity.dart:33-35`). The source comment says that throws because the body is null. `remove` catches `NoResponseDtoError` and still drops the memory row (`activity.dart` store: `77-88`). Any other throw is rethrown, the row stays, and the bubble's `delete` catches it and shows nothing (`comment_bubble.dart:51-56`). Server permission is `activity.delete` (`activity.controller.ts:66`).

### Thumbnail and profile image

These are not activity routes. A row on the album-level screen whose `assetId` is a non-empty string draws that asset's thumbnail (`comment_bubble.dart:31`, `67-78`). The URL is `GET /api/assets/{id}/thumbnail?size=thumbnail&edited=true` (`reference/immich/mobile/lib/presentation/widgets/images/remote_image_provider.dart:21-26`, `reference/immich/mobile/lib/utils/image_url_builder.dart:9-16`). The asset-level screen does not draw that thumbnail. A tap opens the local asset. A miss opens nothing. It is not another activity call (`comment_bubble.dart:35-48`).

Another user's avatar is shown when the row is not their own. The text field shows the signed-in user's avatar. A user whose `profileImagePath` is non-empty is fetched as `{server}/users/{id}/profile-image` (`reference/immich/mobile/lib/widgets/common/user_circle_avatar.dart:38-39`, `61-68`). `hasProfileImage` is that path being non-empty (`reference/immich/mobile/lib/infrastructure/utils/user.converter.dart:7-16`). An empty path draws the first letter of `name` and does not fetch.

### The switch, `PATCH /api/albums/{id}`

- When: the owner toggles comments and likes. The handler sets the switch's local state, then awaits the request. It does not catch (`album_options.page.dart:220-224`).
- Request: `UpdateAlbumDto` with only `isActivityEnabled` (`album_api_repository.dart:119-122`). The rest of this `PATCH` is in the albums note.
- Response: `checkNull`, then `isActivityEnabled` (`album_api_repository.dart:119-123`). The generated parser still reads the whole `AlbumResponseDto`. Required keys are `albumName`, `albumThumbnailAssetId`, `albumUsers`, `assetCount`, `createdAt`, `description`, `hasSharedLink`, `id`, `isActivityEnabled`, `shared`, and `updatedAt` (`immich-openapi-specs.json:19842-19853`). Each `albumUsers` item requires `role` and `user`, and `user` is the same `UserResponseDto` as an activity (`immich-openapi-specs.json:19922-19934`, `33587-33594`). A missing one throws before `isActivityEnabled` is returned. The local column is written only after that returns (`reference/immich/mobile/lib/domain/services/remote_album.service.dart:305-308`, `reference/immich/mobile/lib/infrastructure/repositories/remote_album.repository.dart:362-365`).
- A throw leaves the stored flag unchanged. The switch on this visit stays where the handler set it, because nothing reverts `activityEnabled`. The next open of the options page reads the route album again, which still has the old flag. The comments button reads the stored flag, so it does not move.
- The stored flag is also written from album sync. v3.3.6 asks for `AlbumsV2` (`sync_api.repository.dart:55`). `SyncAlbumV2.isActivityEnabled` is a required boolean (`immich-openapi-specs.json:30304-30336`, `reference/immich/server/src/dtos/sync.dto.ts:240-250`). The handler writes it on insert and on conflict (`reference/immich/mobile/lib/infrastructure/repositories/sync_stream.repository.dart:529-546`). A missing key throws in `fromJson` while the line is parsed (`sync_api.repository.dart:124-138`). That throw leaves `streamChanges` (`sync_api.repository.dart:117-118`). The batch is not handled and not acked (`reference/immich/mobile/lib/domain/services/sync_stream.service.dart:181-188`). The column stays as it was. A row that never landed would use the table default, true (`reference/immich/mobile/lib/data/db/main/table/remote/album.dart:23`). `SyncAlbumV1` has the same required boolean (`sync.dto.ts:226-237`). This app takes `AlbumsV2` against v3.3.6.

## What the screen does with a row

The list is painted newest at the bottom: the page walks `data.reversed` in a reversed list (`activities.page.dart:64-80`).

A like draws a thumb. A comment with non-empty `comment` draws that text. A comment whose `comment` is null or empty draws the name line and no text (`comment_bubble.dart:32`, `97-120`). The name line is `user.name` and `createdAt`. The field is disabled when the route album's `isActivityEnabled` is false, and the hint says the input is disabled (`activity_text_field.dart:76`, `99`). The like button does not read that flag. Create on the server does not either.

The screen does not write SQLite. Delete, create, and list only change the memory cache.
